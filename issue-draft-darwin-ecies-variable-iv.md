=== SUMMARY ===
biometric_cipher (iOS/macOS): миграция с легаси-ECIES на VariableIV + гигиена Darwin — кеширование пробы Secure Enclave и перенос enrollment-маркера биометрии из UserDefaults в Keychain

=== DESCRIPTION (Jira wiki) ===
h2. Описание

Darwin — самый здоровый из бэкендов плагина, радикально менять его не нужно. В задаче три работы:
# перевести шифрование био-обёртки с легаси-варианта ECIES на современный VariableIV, введя версионированный формат обёртки и прозрачную миграцию существующих обёрток;
# кешировать результат пробы Secure Enclave, чтобы не генерировать одноразовый SE-ключ на каждую криптооперацию;
# перенести маркер смены биометрии (enrollment-состояние) из UserDefaults в Keychain.

Первая работа меняет формат шифротекста и требует миграции; две другие — гигиена, не меняющая ни формат, ни схему.

h3. Часть 1 — миграция ECIES: легаси → VariableIV

Сейчас шифрование и расшифрование используют {{.eciesEncryptionCofactorX963SHA256AESGCM}} ({{packages/biometric_cipher/darwin/Classes/Managers/SecureEnclaveManager.swift}}, строки 147 и 167). Apple прямо помечает алгоритм как *Legacy* — «в новом коде используйте …VariableIV…». Разница — в IV для AES-GCM: легаси-вариант всегда использует нулевой, современный выводит случайный из KDF и дополнительно связывает общий секрет как аутентифицируемые данные (AAD).

По отчёту нулевой IV — это легаси, а не дыра: AES-ключ выводится из свежей эфемерной пары на каждый вызов, каждое сообщение шифруется уникальным ключом. Мигрировать всё же стоит: алгоритм деприкейчен, конструкция находится «в одном рефакторинге» от опасной (если кто-то когда-то закеширует выведенный ключ), а внешнему аудитору легаси-константа гарантированно попадёт в отчёт.

Цена: новый вариант *несовместим по шифротексту* — старые обёртки им не расшифровать. Поэтому миграция делается одним релизом с версионированным форматом обёртки:
* первый байт обёртки — версия формата; {{decrypt}} диспетчеризуется по нему;
* при успешной разблокировке со старой обёрткой — прозрачный re-wrap в новый формат (мастер-ключ уже в памяти, шифрование на Darwin не требует промпта — миграция для пользователя невидима);
* чтение старого формата сохраняется минимум два релиза;
* страховка: парольная обёртка независима — худший исход неудачной миграции «пере-включить биометрию», не потеря данных.

h3. Часть 2 — кешировать пробу Secure Enclave

{{isSecureEnclaveSupported()}} ({{SecureEnclaveManager.swift}}, строки 33–56) сегодня *реально генерирует* одноразовый ключ в Secure Enclave — и вызывается как guard при каждой криптооперации ({{BiometricCipherPlugin.swift}}, строки 98, 131, 185, 219, 270: getTPMStatus, generateKey, encrypt, decrypt, deleteKey). Ответ не может измениться за время жизни процесса — достаточно кеша ({{lazy var}}). Чистый выигрыш производительности без какого-либо риска; формат и схема не меняются.

h3. Часть 3 — перенести enrollment-маркер биометрии из UserDefaults в Keychain

Состояние enrollment ({{evaluatedPolicyDomainState}}) хранится в UserDefaults ({{SecureEnclaveManager.swift}}, строки 277–310: save/has/delete/exists; префикс ключа — {{AppConstants.enrollmentStateKeyPrefix}}) — то есть в plist каталога приложения, который можно подменить или сбросить, после чего {{isKeyValid}} ответит неверно. Важно: сам Secure Enclave всё равно откажется расшифровывать инвалидированным ключом, так что это ошибка *диагностики*, не обход защиты — но правильный дом для такого маркера — Keychain с {{kSecAttrAccessibleWhenUnlockedThisDeviceOnly}}. По отчёту этот же маркер пригодится как признак «хранилище существовало» (секция 3 отчёта).

h2. AC

* {{encrypt}} и {{decrypt}} для новых обёрток используют {{.eciesEncryptionCofactorVariableIVX963SHA256AESGCM}}; легаси-константа в пути создания новых обёрток не используется.
* Обёртка версионирована: новые обёртки несут байт версии, {{decrypt}} диспетчеризуется по нему; обёртки старого (легаси) формата продолжают расшифровываться.
* После успешной разблокировки со старой обёрткой выполняется прозрачный re-wrap в новый формат без дополнительного биометрического промпта.
* При сбое миграции данные не теряются: вход по паролю работает, биометрию можно пере-включить.
* Проба Secure Enclave выполняется не более одного раза за жизнь процесса; криптооперации не генерируют одноразовый SE-ключ на каждый вызов.
* Enrollment-маркер хранится в Keychain с {{kSecAttrAccessibleWhenUnlockedThisDeviceOnly}}; чтений/записей enrollment-состояния в UserDefaults в коде не осталось.
* Тесты плагина и {{fvm flutter test}} проходят; поведение на других платформах не изменилось.

h2. Контекст

Секция 4 отчёта «AW-3303 Криптоотчёт». Текущая база Darwin корректна: ключ P-256 генерируется внутри Secure Enclave и не покидает его, доступ ограничен {{kSecAttrAccessibleWhenUnlockedThisDeviceOnly}} и {{.biometryCurrentSet}}, шифрование — системный ECIES со свежей эфемерной парой на каждое сообщение, промпт нужен только на расшифрование. Вердикт отчёта по порядку работ: гигиена (части 2–3) — сразу («это не криптография, а уборка», предаудитный пакет), версионированный формат — как общая инфраструктура для всех платформ, миграция на VariableIV — поверх него (по дорожной карте — после аудита). Рассматривавшаяся альтернатива — ручной ECDH ради AES-256 в био-обёртке — отклонена; асимметрия «пароль AES-256 / биометрия AES-128» документируется в {{SECURITY.md}}, в объём этой задачи не входит. Версионированный формат — та же инфраструктура, что нужна RSA-OAEP-обёртке на Android (секция 5). Развёрнутый разбор — {{docs/AW-321-biometric-cipher-crypto-analysis.md}} (§4.1, §7.3–7.4).

h2. Недостающие детали

* Версионированный формат обёртки — общая инфраструктура для всех платформ; входит ли его реализация в объём этой задачи или выносится отдельным тикетом — не зафиксировано.
* Сроки: по дорожной карте отчёта гигиена (части 2–3) — до аудита, а миграция VariableIV — после аудита поверх версионированного формата; объединение их в одну задачу отклоняется от этой последовательности — планирование по релизам не зафиксировано.
* Судьба уже сохранённых enrollment-маркеров в UserDefaults (мигрировать в Keychain или сбросить с пересохранением при следующей успешной аутентификации) — в отчёте не специфицирована.
