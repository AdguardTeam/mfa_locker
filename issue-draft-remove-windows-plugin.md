=== SUMMARY ===
biometric_cipher: удалить Windows-реализацию плагина — каталог windows/ (~3000 строк кода и тестов), платформу windows из pubspec.yaml и Windows-поля Dart-слоя (вариант B из отчёта AW-3303)

=== DESCRIPTION (Jira wiki) ===
h2. Описание

Вход по Windows Hello отключён на стороне приложения (AW-2957, PR #920), но Windows-реализация плагина никуда не делась: она по-прежнему поставляется и собирается. Схема (подпись Windows Hello от статической строки → SHA-256(подпись) → AES-256-GCM) признана негодной: на unpackaged Win32 ни один примитив ОС не привязывает секрет к приложению — граница проходит по пользователю, и любой процесс того же пользователя может поднять настоящий промпт Hello для нашего ключа (confused deputy, доказано рабочим PoC в AW-2956). Задача — довести решение до конца в кодовой базе: удалить Windows-реализацию целиком (вариант B из секции 6 отчёта «AW-3303 Криптоотчёт», «Пути модификации шифрования: Windows»).

Что удалить (проверено по коду):
* {{packages/biometric_cipher/windows/}} — реализация ~1740 строк ({{biometric_cipher_plugin.cpp}}, {{biometric_cipher_service.cpp}}, репозитории {{windows_hello}} / {{winrt_encrypt}} / {{windows_tpm}}, обёртки NCrypt, {{CMakeLists.txt}}) и {{windows/test/}} ~1220 строк (юнит- и интеграционные тесты, моки).
* {{packages/biometric_cipher/pubspec.yaml}} — платформа {{windows:}} ({{pluginClass: BiometricCipherPluginCApi}}) в {{flutter.plugin.platforms}}; заодно поправить {{description}} пакета — он упоминает Windows.
* Dart-слой: поле {{windowsDataToSign}} в {{packages/biometric_cipher/lib/data/model/config_data.dart}} (объявление, конструктор, from/to map) и поле {{windowsAuthData}} с маппингом в {{windowsDataToSign}} в {{lib/security/models/biometric_config.dart}} (строки 22–23, 30, 41, 47).
* Использования: {{packages/biometric_cipher/test/biometric_cipher_test.dart}} (строка 29) и {{example/lib/features/tpm_test/views/tpm_test_screen.dart}} (строка 44).

Почему это стоит сделать до аудита (из отчёта):
* Аудитор гарантированно разберёт {{SHA-256(подпись)}} как KDF, статический вход и ключ в памяти процесса — и выпишет находки по схеме, которую мы уже признали негодной и отключили. Удалить дешевле, чем объяснять.
* Dart-API на Windows формально живой: достаточно одного места в приложении, чтобы уязвимая схема снова заработала. Удаление убирает риск случайного возврата.
* Бонус: минус ~2700 строк мёртвого кода и build-break MSVC.

Что важно учесть (минусы варианта B по отчёту):
* Нужен путь деградации для установок со старой био-обёрткой; вердикт отчёта также предлагает очистку протухшей био-обёртки при старте.
* При возврате биометрического удобства на Windows обвязку придётся писать заново. Варианты B (удаление) и C (Quick Unlock) взаимоисключающи — задача фиксирует выбор B.

h2. Контекст

Секция 6 отчёта «AW-3303 Криптоотчёт». Исследование AW-2956 (файлы в {{docs/AW-2956/}}: {{research_result.md}}, финальный ревью, PoC с MSIX-кошельком и атакующим exe) доказало атаку confused deputy: биометрию проходит не тот, кто её инициировал — Hello подтверждает присутствие пользователя, а не личность приложения, и аппаратная защита ключа (TPM/NGC) этого не закрывает. AW-2957 (PR #920) отключил вход по Hello — это правильная позиция, и на проде действует вариант A «только пароль» (как у 1Password, Bitwarden, KeePassXC). Схема two-part key из AW-2956 отклонена финальным ревью. Отчёт требует принять решение по варианту B до отправки на внешний аудит. Развёрнутый разбор — {{docs/AW-3303-windows-encryption-paths.md}}.

h2. Недостающие детали

* Механика деградации для установок со старой био-обёрткой (очистка протухшей обёртки при старте) — в объёме этой задачи или отдельной — не зафиксирована.
* Судьба Windows-таргета example-приложения ({{example/windows/}}) не зафиксирована: библиотека остаётся работоспособной на Windows в режиме «только пароль», поэтому таргет может как остаться, так и быть удалён вместе с плагином.
