## Коротко

На Windows проблема не в алгоритме шифрования, а в **модели доступа ОС**. Для обычного (unpackaged) Win32-приложения ни
один примитив Windows — ни Windows Hello, ни TPM, ни DPAPI, ни Credential Locker — **не привязывает локальный секрет к
приложению**: граница безопасности проходит по *пользователю*, а не по *приложению*. Поэтому любой процесс того же
пользователя может вызвать биометрический промпт для нашего ключа, и одно невнимательное подтверждение отдаёт
злоумышленнику мастер-ключ. Это доказано рабочим PoC. Вывод AW-2956: **Windows Hello не может быть самостоятельным
барьером** для ценного секрета на unpackaged Win32. Правильная текущая позиция — вход только по паролю (уже сделано в
AW-2957). Поскольку код отправляется на внешний аудит, к рассмотрению добавлен вариант **полного удаления
Windows-реализации плагина**: сегодня она отключена в приложении, но по-прежнему поставляется и собирается — это ~1700
строк C++, реализующих схему, о которой уже известно, что она сломана.

## Что есть сейчас

Исходная схема (`winrt_encrypt_repository_impl.cpp`): подпись Windows Hello от статической строки →
`SHA-256(подпись)` → AES-256-GCM. Она давала *отдельную* биометрическую обёртку мастер-ключа, то есть Windows Hello был
самостоятельным способом разблокировки, наравне с паролем.

**Временный фикс уже в проде:** [AW-2957](https://jira.int.agrd.dev/browse/AW-2957) (PR #920, смёржен 29.05.2026)
**отключил разблокировку по Windows Hello**. Приложение на Windows работает только по паролю.

**Но код никуда не делся.** Отключение сделано на стороне приложения; библиотека `mfa_locker` по-прежнему содержит и
компилирует полный Windows-бэкенд:

| Что | Объём |
|---|---|
| `packages/biometric_cipher/windows/*.cpp` + заголовки | ~1700 строк реализации |
| `packages/biometric_cipher/windows/test/` | 1013 строк тестов, 12 файлов |
| `pubspec.yaml` | платформа `windows:` объявлена, плагин регистрируется |
| Dart-слой | `windowsAuthData` / `windowsDataToSign` в `biometric_config.dart` |

То есть на аудит уедет живой, собираемый код неработающей по назначению схемы. Это отдельный факт, из которого следует
отдельный вариант решения (вариант B ниже).

## Реальная модель угрозы: confused deputy

Противник в AW-2956 определён точно: **вредоносное ПО, запущенное от имени того же пользователя Windows, без повышения
привилегий**. Такой процесс умеет читать `%APPDATA%` и файл хранилища, скрейпить память запущенного процесса, вызывать
любой user-scoped Windows API и **поднимать настоящее системное окно Windows Hello**.

Сценарий атаки (подтверждён PoC — `demo_msix.mp4`, код `wallet_locker_attack_probe.zip`):

1. Вредонос узнаёт тег, под которым кошелёк хранит ключ (тег — идентификатор, а не секрет).
2. Вредонос **сам** вызывает промпт Windows Hello для этого тега.
3. Невнимательный пользователь видит привычное системное окно и подтверждает биометрию.
4. Вредонос выполняет криптооперацию тем же credential, расшифровывает хранилище и получает сид-фразы в открытом виде.

Ключевой момент: **биометрию проходит не тот, кто её инициировал**. Hello подтверждает *присутствие пользователя на
устройстве*, но не то, что запрос пришёл от нашего приложения. Отсюда название — «запутанный посредник».

## Почему аппаратная защита ключа здесь не помогает

Это главная поправка к прежним заметкам и самый неочевидный вывод исследования. Инстинктивно кажется, что если унести
ключ в TPM и потребовать аппаратно-принудительный жест Hello на расшифрование, атака закроется. **Не закроется** — и по
той же причине, по которой не работает сам Windows Hello.

Аппаратный модуль отвечает на вопрос «извлекаем ли ключ?» — и отвечает хорошо. Но атака вообще не требует извлечения
ключа: злоумышленнику не нужен ключевой материал, ему нужно, чтобы **система выполнила операцию за него**. А на вопрос
«от какого приложения пришёл запрос?» на unpackaged Win32 не отвечает ни один примитив:

| Примитив | Что защищает | По какому признаку авторизует |
|---|---|---|
| Windows Hello / `KeyCredentialManager` (NGC) | ключ не покидает TPM | **пользователь + устройство** |
| TPM напрямую / Platform Crypto Provider | ключ не покидает TPM | **пользователь** |
| DPAPI (`CryptProtectData`) | привязка к учётке и машине | **пользователь + машина** |
| Credential Locker | хранение секрета | **пользователь** |
| Secure Enclave (iOS/macOS), Keystore (Android) | ключ не покидает железо | **приложение** ✅ |

Последняя строка объясняет, почему на iOS/macOS и Android та же архитектура безопасна, а на Windows — нет. Там ОС
привязывает ключ к приложению; здесь — только к пользователю. Поэтому маршрут «перенести ключ в NGC/TPM и включить
обязательный жест» (W1/W2) даёт ровно ту же атаку: вредонос открывает тот же ключ, инициирует обязательный жест,
пользователь подтверждает, вредонос расшифровывает. Аппаратный гейт повышает планку против *кражи ключа*, но против
*confused deputy* не делает ничего.

## Почему остальные идеи тоже не закрывают проблему

| Идея | Почему не работает |
|---|---|
| Спрятать/рандомизировать тег | Тег — идентификатор, а не секрет. Усложняет нецелевую атаку, но процесс того же пользователя всё равно имеет доступ к credential. |
| Своё окно с названием приложения перед Hello | Второе, системное окно Hello кастомизировать нельзя (проверено: `named_window.png` + `second_window.png`); вредонос покажет похожее окно и подведёт пользователя к подтверждению. Снижает риск ошибки пользователя, но техническим барьером не является. |
| `UserConsentVerifier` (как в 1Password/Bitwarden) | Возвращает булев результат, не отдаёт ключевого материала и ничего не подписывает. Вредонос просто **пропускает** проверку и вызывает расшифровку напрямую — classic client-side authorization anti-pattern. |
| MSIX (fullTrust) | Изоляции по приложению **не даёт** — доказано экспериментом: собран MSIX-кошелёк и отдельный атакующий exe, сид-фраза получена. Packaged desktop app по умолчанию работает в full trust. |
| AppContainer / Win32 App Isolation | *Единственная* конфигурация с изоляцией по `User SID + Package Family Name`. Но Flutter не умеет UWP (embedder свернули в 2022), partialTrust ломает доступ к ФС и `file_picker`, приложение не стартовало (белый экран, `app_container_init.log`), а на неподдерживаемых версиях Windows откатывается в fullTrust — уязвимость возвращается. Команда **депроритезировала** путь 19.06.2026. |

**Управляющий принцип исследования:** на unpackaged Win32 никакой примитив ОС не привязывает локальный секрет к
приложению, поэтому Windows Hello не может быть безопасной самостоятельной разблокировкой ценного секрета. Всё
остальное — следствия этого факта.

## Рассмотренные варианты решения (концепция · плюсы · минусы)

### Вариант A — только пароль (AW-2957, уже в проде) — *текущая корректная позиция*
- **Концепция.** Windows Hello как способ разблокировки отключён; мастер-ключ открывается только паролем (Argon2id).
- **Плюсы.** Детерминированно закрывает AW-2956; соответствует модели 1Password / Bitwarden / KeePassXC; уже отгружено.
- **Минусы.** Нет биометрического удобства на Windows.
- Это честный базовый уровень, который любая схема со «спасением Hello» обязана превзойти по безопасности — и против
  заявленной угрозы не превосходит.

### Вариант B — удалить Windows-реализацию плагина — *рекомендуется перед аудитом*
- **Концепция.** Довести решение варианта A до конца в кодовой базе: убрать `packages/biometric_cipher/windows/`
  целиком, снять платформу `windows:` из `pubspec.yaml`, убрать Windows-специфичные поля Dart-слоя
  (`windowsAuthData`, `windowsDataToSign`), а `getBiometryStatus`/`getTPMStatus` на Windows заставить честно
  отвечать «не поддерживается».
- **Плюсы.**
  - **Снимает с аудита заведомые находки.** Аудитор гарантированно разберёт `SHA-256(подпись)` как KDF, статический
    вход, ключ в памяти процесса (F-1, F-2) и потратит на это время ревью — при том что схема уже признана негодной и
    отключена. Удалять дешевле, чем объяснять.
  - **Убирает риск случайного возврата.** Сейчас Dart-API на Windows формально живой: `configure`/`generateKey`/
    `encrypt`/`decrypt` вызываемы, и достаточно одного места в приложении, чтобы уязвимая схема снова заработала.
  - **Снимает поддержку мёртвого кода:** ~2700 строк C++ вместе с тестами, а также известный build-break MSVC
    (`/await` + `<experimental/coroutine>`) на новых тулчейнах.
  - **Честность API.** Сегодня библиотека заявляет поддержку биометрии на Windows, которой по факту нет.
- **Минусы.**
  - Если продукт позже решит вернуть удобство (вариант C), часть обвязки придётся написать заново. Смягчение:
    криптографическое ядро всё равно подлежит переписыванию (challenge-based вместо `SHA-256` от константы), а обвязка
    остаётся в истории git.
  - Нужен аккуратный путь деградации: у существующих установок в хранилище может лежать био-обёртка (`Origin.bio`) —
    приложение обязано молча падать на парольный путь, а «протухшую» обёртку лучше подчищать при старте (это же
    действие есть в плане AW-2956 §1.3).
- **Решение о варианте B нужно принять до аудита**, потому что оно взаимоисключающе с вариантом C.

### Вариант C — «Quick Unlock», сделанный правильно — *только если удобство биометрии обязательно как продуктовое требование*
- **Концепция.** Корень доверия — пароль, обязателен на каждом холодном старте и после перезагрузки. Windows Hello лишь
  сокращает повторную разблокировку *внутри уже аутентифицированной паролем сессии* и никогда не является входом,
  равным паролю. Значение от Hello — TPM-backed, подписывает *свежий одноразовый challenge*, живёт только в памяти.
- **Плюсы.** Даёт биометрическое удобство; убирает свойство «подписал один раз — выводи ключ вечно»
  (офлайн-воспроизводимый KEK), которое делало AW-2956 тяжёлой; совпадает с тем, как устроены KeePassXC Quick Unlock и
  Bitwarden после фикса CVE-2023-27706.
- **Минусы.** Это **удобство, а не барьер**: от гонки «вредонос против пользователя» в моменте не спасает (на Windows
  без изоляции приложения не спасает ничто). Приемлемо только при честной маркировке «convenience»; подавать как
  «безопасный Hello» — вводить в заблуждение. Возврат Windows-кода заново поднимает build-break MSVC — расход, который
  надо заложить заранее.

### Вариант D — AppContainer / Win32 App Isolation — *под вопросом, зависит от эксперимента*
- **Концепция.** Запуск в AppContainer/appSilo, где ОС изолирует credential по `User SID + PFN`.
- **Плюсы.** Единственный путь вернуть настоящую привязку секрета к приложению на Windows.
- **Минусы.** Preview-only (Win11 24H2+); нет пути упаковки во Flutter; риск для всех нативных плагинов, работающих с
  ФС; выигрыш против unpackaged-атакующего не доказан; уже депроритезирован. Не ближнесрочное решение.

### Вариант E — аппаратный корень доверия — *дальний горизонт*
- **Концепция.** Держать ключ подписи вне общей поверхности ОС — аппаратное устройство (тип Ledger) или внешний аутентификатор.
- **Плюсы.** Единственный способ сделать локальный ценный секрет действительно устойчивым к same-user-вредоносу на Windows.
- **Минусы.** Большой объём работ, отдельная продуктовая история. Отмечено для полноты, не предлагается сейчас.

## Разбор предложенной схемы «two-part key» (и почему она не фикс)

Промежуточный ресёрч (`approach_of_windows_hello_usage.md`) предложил разделить мастер-ключ на две части и собирать их
после проверки Hello. Финальный ревью (`windows-hello-two-part-key-validation.html`) разобрал её и **отклонил как
решение**. Две вариации:

- **«В памяти».** Пароль вводится всегда, из него выводится первая часть ключа и держится в памяти ~5 минут; в это окно
  Hello достаёт вторую часть. → По сути это и есть Quick Unlock из варианта C: приемлемо, но *только* как удобство.
- **«DPAPI `device_secret` + пароль → KEK», пароль «сохраняется на неопределённое время».** → **Пересобирает AW-2956** и
  строго хуже, чем AW-2957. Отгружать нельзя.

Пять несущих изъянов из ревью:

1. **`UserConsentVerifier` — не криптографический фактор.** Возвращает enum, не отдаёт ключ; ветка «if Verified →
   CryptUnprotectData» живёт внутри процесса самого приложения. Вредонос её просто не вызывает.
2. **DPAPI `device_secret` — user-scoped, а не app-scoped.** Любой процесс того же пользователя вызывает
   `CryptUnprotectData`. Это ровно механизм CVE-2023-27706 у Bitwarden («Bitwarden Heist»), который им пришлось убрать.
3. **Разделение ключа ничего не даёт, если обе части за одной границей.** Против same-user-вредоноса достижимы обе;
   «defense-in-depth» здесь — театр. (Разделение реально помогает лишь против офлайн-кражи файла на другую машину — но
   это не угроза AW-2956, и Argon2id уже даёт офлайн-стойкость.)
4. **«Сохранить пароль на неопределённое время» пересобирает AW-2956** — хранилище пароля снова user-scoped. Фатально.
5. **Ссылается на уязвимый паттерн, а не на исправленный.** Bitwarden после CVE ушёл на живую подпись через
   KeyCredentialManager; 1Password прямо пишет, что корень доверия — пароль, а Hello — удобство.

Что в предложении ценного: **пароль становится обязательным** (правильное направление) и идея короткоживущего
сессионного кеша (это и есть Quick Unlock). Криптографические заявления про `UserConsentVerifier` и DPAPI надо отбросить.

## Вердикт по Windows

Windows — единственная платформа, где корень проблемы не в криптографии, а в модели доступа ОС, и это меняет сам
характер задачи: «модифицировать алгоритм шифрования» здесь бессмысленно, потому что любая внутрипроцессная схема на
unpackaged Win32 упирается в границу «пользователь, а не приложение». Аппаратная защита ключа (TPM) эту границу не
сдвигает.

- **Оставить AW-2957 (только пароль)** как корректную текущую позицию; добавить очистку протухшей био-обёртки при старте.
- **Принять решение по варианту B до аудита.** Если биометрия на Windows не планируется в обозримом релизе — удалить
  Windows-реализацию плагина: она отключена, но поставляется, и на аудите превратится в набор находок про схему,
  которую мы и так признали негодной.
- **Не принимать** схему two-part key как фикс (против угрозы она в лучшем случае равна паролю, а в варианте с
  персистом пароля пересобирает уязвимость).
- **Биометрия на Windows — продуктовое решение**, не инженерное: если удобство обязательно, реализовать вариант C
  (Quick Unlock) с корректной криптографией и честной маркировкой «удобство поверх пароля».
- **Не** персистить пароль или эквивалент мастер-ключа; **не** считать успех `UserConsentVerifier` авторизацией
  расшифровки; **не** подавать никакую unpackaged-Win32-схему как безопасный самостоятельный вход по Hello.

Windows-контракт неизбежно отличается от iOS/macOS/Android: там `encrypt` без промпта и `decrypt` с промптом безопасны,
потому что ОС привязывает ключ к приложению. На Windows такой привязки нет — и это ограничение платформы, а не нашего кода.
