## Коротко

На Windows проблема не в алгоритме шифрования как таковом, а в **модели доступа ОС**. Для обычного (unpackaged)
Win32-приложения ни один примитив Windows — ни Windows Hello, ни DPAPI, ни Credential Locker — **не привязывает
локальный секрет к приложению**: граница безопасности проходит по *пользователю*, а не по *приложению*. Поэтому любой
процесс того же пользователя может вызвать биометрический промпт для нашего ключа, и невнимательное подтверждение
пользователем отдаёт злоумышленнику мастер-ключ. Это доказано рабочим PoC. Вывод AW-2956: **API Windows Hello не
способно быть самостоятельным барьером** для ценного секрета на unpackaged Win32. Правильная текущая позиция —
парольный вход (уже сделано в AW-2957); биометрия на Windows допустима **только как удобство поверх пароля**, честно
маркированное как таковое, а не как замена паролю. Замена схемы шифрования проблему не решает — решает смена модели
доверия.

## Что есть сейчас

Исходная схема (`winrt_encrypt_repository_impl.cpp`): подпись Windows Hello от статической строки →
`SHA-256(подпись)` → AES-256-GCM. Она давала *отдельную* биометрическую обёртку мастер-ключа — то есть Windows Hello
был самостоятельным способом разблокировки, наравне с паролем.

**Временный фикс уже в проде:** [AW-2957](https://jira.int.agrd.dev/browse/AW-2957) (PR #920, смёржен 29.05.2026)
**отключил разблокировку по Windows Hello** на Windows. Сейчас платформа работает только по паролю. Это не заглушка на
время, а осознанно выбранная безопасная база — см. вердикт.

## Реальная модель угрозы: confused deputy

Противник в AW-2956 определён точно: **вредоносное ПО, запущенное от имени того же пользователя Windows, без повышения
привилегий**. Такой процесс умеет: читать `%APPDATA%` и файл хранилища, скрейпить память запущенного процесса,
вызывать любой user-scoped Windows API и **поднимать настоящее системное окно Windows Hello**.

Сценарий атаки (подтверждён PoC — `demo_msix.mp4` + код `wallet_locker_attack_probe.zip`):

1. Вредонос узнаёт тег, под которым кошелёк хранит ключ (тег — идентификатор, а не секрет).
2. Вредонос сам вызывает `KeyCredentialManager.OpenAsync` / промпт Windows Hello для этого тега.
3. Невнимательный пользователь видит привычное окно Hello и подтверждает биометрию.
4. Вредонос выполняет криптооперацию тем же credential и расшифровывает хранилище → получает сид-фразы в открытом виде.

Ключевой момент: **биометрию проходит не тот, кто её инициировал**. Hello подтверждает *присутствие пользователя на
устройстве*, но не то, что запрос пришёл от нашего приложения. Отсюда и название — «запутанный посредник».

## Почему API Windows Hello это не закрывает

Исследование прошло по всем очевидным идеям и уперлось в один и тот же корень.

| Идея | Почему не работает |
|---|---|
| Спрятать/рандомизировать тег | Тег — идентификатор, а не секрет. Случайное имя усложняет нецелевую атаку, но не закрывает корень: процесс того же пользователя всё равно имеет доступ к credential. |
| TPM / аппаратный ключ | TPM защищает ключ *от извлечения*, но не отличает легитимный запрос приложения от запроса другого процесса того же пользователя, если пользователь подтвердил Hello. **Именно поэтому снят маршрут W1/W2.** |
| Своё окно с названием приложения перед Hello | Второе, системное окно Hello кастомизировать нельзя (проверено, `named_window.png` + `second_window.png`); вредонос может показать похожее окно и подвести пользователя к подтверждению. Снижает риск ошибки пользователя, но не является техническим барьером. |
| `UserConsentVerifier` (как в 1Password/Bitwarden) | Возвращает булев результат `Verified/…`, не отдаёт ключевого материала и ничего не подписывает. Вредонос просто **пропускает** проверку и вызывает расшифровку напрямую. Это client-side authorization anti-pattern. |
| MSIX (fullTrust) | Изоляции по приложению **не даёт** — доказано экспериментом: собран MSIX-кошелёк и отдельный атакующий exe, сид-фраза получена. Packaged desktop app по умолчанию работает в full trust, credential остаётся в границе пользователя. |
| AppContainer / Win32 App Isolation | *Единственная* конфигурация с изоляцией по `User SID + Package Family Name`. Но: Flutter не умеет UWP (embedder свернули в 2022), partialTrust ломает доступ к ФС и `file_picker`, приложение не стартовало (белый экран, `app_container_init.log`). На неподдерживаемых версиях Windows откатывается в fullTrust — уязвимость возвращается. Команда **депроритезировала** этот путь (19.06.2026). |

**Управляющий принцип исследования:** на unpackaged Win32 никакой примитив ОС не привязывает локальный секрет к
приложению, поэтому Windows Hello не может быть безопасной самостоятельной разблокировкой ценного секрета. Всё
остальное — производные этого факта.

## Рассмотренные варианты решения (концепция · плюсы · минусы)

### Вариант A — только пароль (AW-2957, уже в проде) — *наименьший риск*
- **Концепция.** Windows Hello как способ разблокировки отключён; мастер-ключ открывается только паролем (Argon2id).
- **Плюсы.** Детерминированно закрывает AW-2956; соответствует модели 1Password / Bitwarden / KeePassXC; минимум кода;
  уже отгружено.
- **Минусы.** Нет биометрического удобства на Windows.
- **Это честный базовый уровень, который любая схема со «спасением Hello» обязана превзойти по безопасности — и против
  заявленной угрозы не превосходит.**

### Вариант B — «Quick Unlock», сделанный правильно — *рекомендуется, если удобство биометрии обязательно как продуктовое требование*
- **Концепция.** Корень доверия — пароль, он обязателен на каждом холодном старте и после перезагрузки. Windows Hello
  лишь сокращает повторную разблокировку *внутри уже аутентифицированной паролем сессии*, но никогда не является
  самостоятельным входом, равным паролю. Значение от Hello — TPM-backed, подписывает *свежий одноразовый challenge* и
  живёт только в памяти.
- **Плюсы.** Даёт биометрическое удобство; убирает свойство «подписал один раз — выводи ключ вечно» (офлайн-воспроизводимый
  KEK), которое делало AW-2956 тяжёлой; совпадает с тем, как устроены KeePassXC Quick Unlock и Bitwarden после фикса.
- **Минусы.** Это **удобство, а не барьер**: от гонки «вредонос против пользователя» в моменте оно не спасает (на
  Windows от этого не спасает ничто без изоляции приложения). Приемлемо только при честной маркировке «convenience»;
  подавать это как «безопасный Hello» — вводить в заблуждение. Возврат `biometric_cipher`/KeyCredentialManager на
  Windows заново поднимает известный build-break MSVC (`/await` + `<experimental/coroutine>`) — расход, который надо
  заложить заранее.

### Вариант C — AppContainer / Win32 App Isolation — *под вопросом, зависит от эксперимента*
- **Концепция.** Запуск в AppContainer/appSilo, где ОС изолирует credential по `User SID + PFN`.
- **Плюсы.** Единственный путь вернуть *настоящую* привязку секрета к приложению на Windows.
- **Минусы.** Preview-only (Win11 24H2+); нет пути упаковки во Flutter; риск для всех нативных плагинов, работающих с
  ФС; выигрыш против unpackaged-атакующего не доказан; уже депроритезирован. Не ближнесрочное решение.

### Вариант D — аппаратный корень доверия — *дальний горизонт*
- **Концепция.** Держать ключ подписи вне общей поверхности ОС — аппаратное устройство (тип Ledger) или внешний
  аутентификатор.
- **Плюсы.** Единственный способ сделать локальный ценный секрет действительно устойчивым к same-user-вредоносу на Windows.
- **Минусы.** Большой объём работ; отдельная продуктовая история. Отмечено для полноты, не предлагается сейчас.

## Разбор предложенной схемы «two-part key» (и почему она не фикс)

Промежуточный ресёрч (`approach_of_windows_hello_usage.md`) предложил разделить мастер-ключ на две части и собирать их
после проверки Hello. Финальный ревью (`windows-hello-two-part-key-validation.html`) разобрал её и **отклонил как
решение**. Две вариации:

- **Вариант «в памяти» (A-подобный).** Пароль вводится всегда, из него выводится первая часть ключа и держится в памяти
  ~5 минут; в это окно Hello достаёт вторую часть. → По сути это и есть Quick Unlock из варианта B — приемлемо, но
  *только* как удобство.
- **Вариант «DPAPI device_secret + пароль → KEK», пароль «сохраняется на неопределённое время».** → **Пересобирает
  AW-2956** и строго хуже, чем AW-2957. Отгружать нельзя.

Пять несущих изъянов из ревью:

1. **`UserConsentVerifier` — не криптографический фактор.** Возвращает enum, не отдаёт ключ; шаг «if Verified →
   CryptUnprotectData» живёт внутри процесса самого приложения. Вредонос его просто не вызывает.
2. **DPAPI `device_secret` — user-scoped, а не app-scoped.** Любой процесс того же пользователя вызывает
   `CryptUnprotectData`. Это ровно механизм CVE-2023-27706 у Bitwarden («Bitwarden Heist»), который им пришлось убрать.
3. **Разделение ключа ничего не даёт, если обе части за одной границей.** Против same-user-вредоноса обе части
   достижимы; «defense-in-depth» здесь — театр. (Разделение реально помогает лишь против *офлайн-кражи файла на другую
   машину* — но это не угроза AW-2956, и Argon2id уже даёт офлайн-стойкость.)
4. **«Сохранить пароль на неопределённое время» пересобирает AW-2956** — хранилище пароля снова user-scoped, вредонос
   его читает. Фатально.
5. **Ссылается на уязвимый паттерн, а не на исправленный.** Bitwarden после CVE ушёл на живую подпись через
   KeyCredentialManager; 1Password прямо пишет, что корень доверия — пароль, а Hello — удобство.

Что в предложении ценного (и что стоит забрать): **пароль становится обязательным** (правильное направление);
DPAPI-привязка к устройству как дёшевая защита от офлайн-кражи файла; идея короткоживущего сессионного кеша (это и есть
Quick Unlock). Но криптографические заявления про `UserConsentVerifier` и DPAPI надо отбросить.

## Немедленные меры — независимо от выбора

1. **Оставить AW-2957 (только пароль) как текущую корректную позицию** и добавить очистку «протухшего» ключа при
   старте (action plan §1.3 из AW-2956).
2. **Если Hello возвращается — только как Quick Unlock (вариант B)**, с обязательными правилами: пароль на каждом
   холодном старте; Hello подписывает *свежий одноразовый challenge*, TPM-backed, результат только в памяти; никогда не
   персистить пароль или эквивалент мастер-ключа.
3. **Дёшевая defense-in-depth только вместе с п.2:** рандомный тег и рандомная строка-для-подписи на инсталляцию —
   границу не меняют, но повышают стоимость нецелевого массового вредоноса. Сами по себе бесполезны.

## Вердикт по Windows

Windows — единственная платформа, где корень проблемы не в криптографии, а в модели доступа ОС, и это **меняет сам
характер задачи**: «модифицировать алгоритм шифрования» здесь бессмысленно, потому что любая внутрипроцессная схема на
unpackaged Win32 упирается в границу «пользователь, а не приложение».

- **Оставить AW-2957 (только пароль)** как корректную текущую позицию; добавить очистку протухшего ключа при старте.
- **Не принимать** схему two-part key как фикс (против угрозы она в лучшем случае равна паролю, а в варианте с
  персистом пароля — пересобирает уязвимость).
- **Биометрия на Windows — продуктовое решение**, не инженерное: если удобство обязательно, реализовать вариант B
  (Quick Unlock) с корректной криптографией и честной маркировкой «удобство поверх пароля», а не «безопасный Hello».
- **Не** персистить пароль/эквивалент мастер-ключа; **не** считать успех `UserConsentVerifier` авторизацией
  расшифровки; **не** подавать никакую unpackaged-Win32-схему как безопасный самостоятельный вход по Hello.

Windows-контракт при этом отличается от iOS/macOS/Android: там `encrypt` без промпта и `decrypt` с промптом —
безопасная модель, потому что ключ привязан к аппаратному модулю *и* к процессу через ОС. На Windows такой привязки к
приложению нет, поэтому Hello не может нести ту же роль — и это ограничение платформы, а не нашего кода.
