01

The verdict

Recommendation
Close AW-321. What it asks for is already in the codebase.

The ticket asks to “implement an iOS/macOS version using a combination of asymmetric and symmetric cryptography with the Secure Enclave.” The Darwin backend already does exactly that. It calls SecKeyCreateEncryptedData with the algorithm .eciesEncryptionCofactorX963SHA256AESGCM — and ECIES is the combination of asymmetric and symmetric cryptography the ticket describes.

Implementing the ticket as written would produce what already ships. The interesting problems are on the other two platforms.

What the algorithm constant actually means

This is not an inference. Apple's own SecKey.h, shipped with the local SDK, documents the exact constant the plugin uses:

kSecKeyAlgorithmECIESEncryptionCofactorX963SHA256AESGCM
Legacy ECIES encryption or decryption, use kSecKeyAlgorithmECIESEncryptionCofactorVariableIVX963SHA256AESGCM in new code. Encryption is done using AES-GCM with key negotiated by kSecKeyAlgorithmECDHKeyExchangeCofactorX963SHA256. AES Key size is 128bit for EC keys <=256bit and 256bit for bigger EC keys. Ephemeral public key data is used as sharedInfo for KDF. AES-GCM uses 16 bytes long TAG and all-zero 16 byte long IV. MacOSX26.5.sdk · Security.framework · SecKey.h, lines 1152–1157

Read that as a pipeline and it is textbook hybrid cryptography: generate an ephemeral P-256 keypair → cofactor ECDH against the Secure Enclave's public key → ANSI X9.63 KDF with SHA-256 → AES-GCM over the payload. Asymmetric key agreement, symmetric bulk encryption, private half never leaving the enclave.

Three reasons not to reopen it

  1. It is already done. See above.
  2. The premise has aged out. Filed 2024-12-03 at P4, due 2025-05-30, PR declined. The branch has zero commits. Meanwhile the Darwin code has been substantially reworked since — enrollment tracking, isKeyValid, macOS-specific handling — all landed via AW-2526, AW-2662 and AW-3071.
  3. Darwin is the healthiest backend of the three. Effort there has the lowest marginal return. Both High-severity findings are on Windows; most actionable Mediums are on Android.
But the instinct behind the ticket was right. A hybrid design is the correct shape here for one specific reason: it lets you encrypt without authenticating. Only the public half is needed to wrap a new master key, so re-wrapping costs no biometric prompt. Android and Windows both prompt on encrypt today. So the useful reading of AW-321 inverts it — the model iOS already has is the one the other platforms should adopt.
02

What the plugin actually protects

Easy to get wrong, and it changes how you judge everything downstream: the biometric cipher is not bulk encryption. It is a key-wrapping primitive, and the thing it wraps is 32 bytes long.

lib/storage/encrypted_storage_impl.dart : 165 Dart 
// The biometric cipher never sees vault contents — only the master key.
final encryptedMasterKey = await newWrapFunc.encrypt(masterKey);

Three consequences worth carrying into the rest of the report:

  • Payloads are tiny. 32 bytes, 44 after the Dart-side base64. Per-message asymmetric overhead is irrelevant — the ECIES ephemeral public key adds 65 bytes to something that is already negligible.
  • The wrap caps the biometric path's strength. Wrapping a 256-bit key under a 128-bit key means the biometric route offers 128-bit security. That happens on two of the three platforms — inherently on Darwin, accidentally on Android.
  • Compromise is total but recoverable. Anyone who obtains the wrap key obtains the master key, and therefore the vault. But the password wrap is an independent path, so a broken biometric enrollment is an inconvenience, not data loss.
03

iOS & macOS — Secure Enclave ECIES

The strongest of the three. The private key is generated inside the Secure Enclave and never leaves it; the app only ever holds a reference.

Key generation and access control

The access-control configuration is the single most important thing on this platform, and it is correct:

packages/biometric_cipher/darwin/Classes/Managers/AuthenticationManager.swift : 31–57 Swift 
static func getAccessControl(_ context: LAContextProtocol) throws -> SecAccessControl {
    let isBiometrySupported = try isBiometrySupported(context)

    var accessFlags: SecAccessControlCreateFlags = [.privateKeyUsage]
    if isBiometrySupported {
        accessFlags.insert(.biometryCurrentSet)   // ← key dies on re-enrollment
    } else {
        accessFlags.insert(.userPresence)
    }

    var error: Unmanaged<CFError>?
    guard let accessControl = SecAccessControlCreateWithFlags(
        kCFAllocatorDefault,
        kSecAttrAccessibleWhenUnlockedThisDeviceOnly,   // never backed up
        accessFlags,
        &error
    ) else {
        throw AuthenticationError.secAccessCreateControl(error?.takeRetainedValue() as Error?)
    }

    return accessControl
}

.biometryCurrentSet means the OS destroys the key the moment the enrollment set changes — a new fingerprint, a re-registered face. That is exactly the property you want, and it is enforced by the platform rather than by application logic. Android matches it. Windows does not.

The encryption path

packages/biometric_cipher/darwin/Classes/Managers/SecureEnclaveManager.swift : 132–158 Swift 
func encrypt(_ encryptionString: String, tag: String) throws -> Data {
    let privateKeyTag = try getTagData(tag: tag)
    let privateKey = try requirePrivateKey(tag: privateKeyTag)

    // Deriving the public half needs no authentication — this is why
    // encryption on Darwin is prompt-free.
    guard let publicKey = try getPublicKey(privateKey: privateKey) else {
        throw SecureEnclaveManagerError.failedGetPublicKey
    }

    let algorithm: SecKeyAlgorithm = .eciesEncryptionCofactorX963SHA256AESGCM

    guard keychainService.isAlgorithmSupported(key: publicKey,
                                               operation: .encrypt,
                                               algorithm: algorithm) else {
        throw SecureEnclaveManagerError.encryptionAlgorithmNotSupported
    }

    return try keychainService.encryptData(key: publicKey,
                                          algorithm: algorithm,
                                          data: encryptionData) as Data
}

Is the all-zero IV a vulnerability?

No — not as used here. GCM nonce reuse is catastrophic only when the same (key, nonce) pair encrypts two different plaintexts. Every call generates a fresh ephemeral keypair, so every message gets a unique AES key and the constant IV never repeats against the same key. This is precisely why Apple shipped the variant at all.

It should still move to the VariableIV form — Apple labels this one “Legacy”, and it is one careless refactor (caching the derived key) away from being dangerous. But that is hygiene, not an incident, and it breaks the ciphertext format. See the roadmap.

AES-128, and no way around it

The Secure Enclave only supports 256-bit ECC. Per the header quoted in §1, that means ECIES on the enclave always yields AES-128-GCM — there is no parameter to change. So the biometric wrap of the AES-256 master key runs at 128-bit strength. Not broken, not urgent, but a real asymmetry against the password path that is documented nowhere.

And the hardware-backing check that the whole enablement flow gates on:

override fun getTPMStatus(): TPMStatus = TPMStatus.SUPPORTED
// Hardcoded. Android claims hardware backing unconditionally, and

AndroidKeyStore keys are not guaranteed to be hardware-backed. On a device with no TEE or a broken keymaster, the key can be software-backed — sitting in the same memory the app runs in — while the user is told “TPM: supported”. KeyInfo.isInsideSecureHardware (API 23+) or KeyInfo.getSecurityLevel() (API 31+) answers this honestly.

05

Windows — a signature used as key material

The outlier, and where both High-severity findings live. Windows Hello signs a fixed string; the signature is hashed to 32 bytes; that hash is the AES key. Everything problematic follows from those three steps.

packages/biometric_cipher/windows/winrt_encrypt_repository_impl.cpp : 19–29 C++ / WinRT 
CryptographicKey WinrtEncryptRepositoryImpl::CreateAESKey(const IBuffer signature) const
{
    auto sha256Provider = HashAlgorithmProvider::OpenAlgorithm(HashAlgorithmNames::Sha256());
    auto sha256Hash = sha256Provider.HashData(signature);
    // ↑ A bare hash is not a KDF: no salt, no info string, no domain separation.
    if (sha256Hash.Length() != 32) {
        throw hresult_error(error_fail, L"Hash length is not 32 bytes.");
    }

    auto aesProvider = SymmetricKeyAlgorithmProvider::OpenAlgorithm(SymmetricAlgorithmNames::AesGcm());
    return aesProvider.CreateSymmetricKey(sha256Hash);   // key now lives in this process
}
packages/biometric_cipher/windows/biometric_cipher_service.cpp : 82–95 C++ / WinRT 
auto& configData = m_ConfigStorage->GetConfig();

// dataToSign defaults to the constant "locker_authentication_request"
// (lib/security/models/biometric_config.dart) — the same input, every time.

auto&& signature  = CryptographicBuffer::ConvertStringToBinary(dataToSign, BinaryStringEncoding::Utf16LE);
auto&& aesKey     = co_await CreateAESKeyAsync(hTag, signature);
auto&& encryptedBase64String = m_WinrtEncryptRepository->Encrypt(aesKey, hData);

The dependency nobody wrote down

The scheme only works if RequestSignAsync returns byte-identical output for identical input, forever. Nothing in the code, comments or docs says so. It holds today because Windows Hello KeyCredential uses RSA with PKCS#1 v1.5 padding, which is deterministic — but that is a platform implementation detail, not a contract Microsoft guarantees.

If Windows ever migrates those credentials to RSA-PSS or ECDSA — both randomised, both what a modern platform would move to — then SHA-256(signature) yields a different key on every call and every existing vault's biometric path breaks permanently, with no migration route and no advance warning. The data survives via the password wrap; the enrollment does not.

And a weaker notion of “biometric”

Windows Hello treats a PIN as a first-class credential. On a machine configured that way, RequestSignAsync is satisfied by typing the PIN — no biometric involved, and no way for the calling app to tell. Hello credentials also survive fingerprint re-enrollment, so the invalidation guarantee that Darwin and Android get from the OS simply does not exist here.

Both High-severity findings sit on Windows, and both stem from the same design decision — using a Hello signature as key material. Darwin's three are hygiene and performance, not exposure.

The two that matter

F-1 High Windows

The AES key is derived by a bare hash and lives in process memory

SHA-256(signature) is not a key-derivation function: no salt, no info string, no domain separation, no iteration. Because dataToSign is a fixed constant, the derived key is identical on every call for the lifetime of the enrollment — a long-lived static key wearing a costume.

Worse, unlike Darwin and Android, the raw 32-byte key is materialised in the app's address space as a CryptographicKey. A debugger, a memory scraper, or an uploaded crash dump recovers a key that decrypts the vault forever, with no biometric prompt ever again. The TPM check in GetTPMStatusAsync is honest about the TPM's presence but decorative with respect to the data.

Fix Use HKDF (KeyDerivationAlgorithmNames.Sp800108CtrHmacSha256, available on the platform) rather than a raw hash — or better, stop deriving from the signature entirely and hold the wrap key in CNG/DPAPI-NG bound to the TPM and gated on Hello, so it never enters the process.
F-2 High Windows

Undocumented dependency on Windows Hello signature determinism

The whole backend rests on RequestSignAsync being byte-for-byte reproducible. True today (RSA PKCS#1 v1.5), unguaranteed tomorrow. A platform move to RSA-PSS or ECDSA silently breaks every Windows user's biometric enrollment at once, with no detection and no migration path.

Fix — cheapest first 1 · Document the assumption in code and in SECURITY.md, so nobody “modernises” it unaware. 2 · Store a verifier — SHA-256(derived_key ‖ salt) — at enrollment and check it before decrypting, turning a silent failure into a clear “re-enroll biometrics” state. 3 · Remove the dependency altogether via the F-1 fix.

What was built

The PR did not touch the existing plugin. It created a second, parallel federated plugin — packages/secure_mnemonic, described in its own pubspec as “AdGuard TPM plugin” — and wired a debug card into the exchange screen so the result could be poked by hand.

The cryptography it proposed

This is the substance, and it is a genuinely different construction from what ships. It reaches for CryptoKit's SecureEnclave.P256.KeyAgreement instead of SecKeyCreateEncryptedData, and derives its own symmetric key by hand.

packages/secure_mnemonic/ios/Classes/SecureEnclaveManager.swift · PR #112 Swift 
// Called by BOTH encrypt and decrypt.
private func deriveSymmetricKey(tag: Data) throws -> SymmetricKey {
    let privateKey   = try getPrivateKey(tag: tag)
    let salt         = generateRandomSalt()              // ← 32 fresh bytes, every call
    let sharedSecret = try privateKey.sharedSecretFromKeyAgreement(
        with: privateKey.publicKey)                     // ← ECDH with itself

    return sharedSecret.hkdfDerivedSymmetricKey(
        using: SHA256.self, salt: salt, sharedInfo: tag, outputByteCount: 32)
}

Three ways it could not work

P-1 Blocker iOS

The random salt makes decryption mathematically impossible

generateRandomSalt() returns 32 fresh SecRandomCopyBytes on every call, and the salt is never persisted, never returned, and never embedded in the ciphertext. Encryption derives K₁ = HKDF(secret, salt₁, tag); decryption derives K₂ = HKDF(secret, salt₂, tag). AES.GCM.open fails tag verification, always.

The nonce is handled correctly — CryptoKit generates it and sealedBox.combined carries it — which makes the omission specific to the salt, and makes it look like an oversight rather than a misunderstanding. Either way, the round trip cannot close. This is the strongest single piece of evidence that the branch never ran successfully on a device.

P-2 Blocker Channel

The method names do not match across the channel

Independently of P-1, the key can never be created from Dart:

Dart sendsiOS acceptsResult

The channel names diverge too. Dart and iOS agree on secure_enclave; the macOS and Android plugins both register secure_mnemonic. Neither is addressable from the Dart side at all.

P-3 Blocker iOS

generateKeyPair never completes its result on success

do {
    try enclaveManager.generateAndStoreKeys(tag: tag)   // no result(nil) here
} catch let error as BaseError {
    result(getFlutterError(error))
} catch { … }

Every other handler calls result(…) on the success path. This one does not, so a successful key generation leaves the Dart Future pending forever. Combined with P-2 the call never arrives, which is presumably why nobody noticed.

What survived anyway

The PR's structure is the direct ancestor of today's Darwin backend, and the resemblance is not vague. AppConstants.privateKeyTag = "com.adguard.tpm.secureEnclavePrivateKey" is byte-identical in both. So is the shape of protocol BaseError: LocalizedError with its machine-readable code, mapped into a FlutterError at the plugin boundary. SecureKeychainManager became KeychainService, Authentication became AuthenticationManager, Base64Manager became Base64Codec, and the plugin → manager → service decomposition is unchanged, now with protocols for testability.

So PR #112 is best read as the prototype whose architecture shipped and whose cryptography did not. The skeleton was kept; hand-rolled HKDF over a self-ECDH secret was replaced by SecKeyCreateEncryptedData, which performs the same hybrid construction inside Apple's audited implementation — with a fresh ephemeral key per message, and without prompting on encrypt.

What this changes
The PR was not declined for lack of time. It was declined because it did not work.

§01's second reason — “the premise has aged out” — can now be put more strongly. The branch could not decrypt, could not be called from Dart, and never covered half its stated platform scope. Once repaired it would have been weaker than what already existed on every property that matters except key length.

Nothing in it is worth resurrecting. Its architectural contribution is already merged and improved on; its cryptographic contribution is a design a reviewer correctly rejected. And note that the residual scope in §09 — AES-256 on Darwin via manual ECDH — only resembles this: that proposal uses a genuine ephemeral counterparty key with a stored salt and AAD binding. The failure of PR #112 says nothing about its viability.

09

Improvement options

Four candidate directions, assessed. Two are worth building, one is worth documenting instead, and one is the ticket as written.

Build

Rework Windows key protection

Use Hello for authentication rather than as key material, with the wrap key held in CNG/DPAPI-NG bound to the TPM. Brings Windows in line with the other two platforms' “key never enters the process” property.

Resolves
F-1, F-2, and most of F-6
Cost
High — new C++ surface, format migration
Risk if skipped
Silent, unrecoverable enrollment breakage
Build

Versioned ciphertext format

A version byte prefix, AAD binding version ‖ tag, and transparent re-wrap on first successful unlock. Several other recommendations queue behind this one — do the format change once, not four times.

Resolves
F-8, F-14; unblocks the rest
Cost
Medium — touches all three natives
Note
The master key is in hand at unlock, so re-wrap needs no extra prompt
Document, don't build

AES-256 on Darwin via manual ECDH

Escaping AES-128 means abandoning SecKeyCreateEncryptedData for SecKeyCopyKeyExchangeResult plus your own HKDF and nonce management. It works — but it trades an audited Apple implementation for one that must be reviewed from scratch, to close a gap that is not a practical weakness.

Verdict
Not worth the risk today
Revisit if
A compliance rule mandates 256-bit throughout
Don't build

Open questions

Is the 128-bit biometric wrap acceptable?

Not a practical weakness — but if a compliance regime requires 256-bit throughout, that changes the calculus on manual ECDH considerably.

Is Windows first-class, or best-effort?

This decides whether R-14 is a P2 or a “document and accept”. The declined PR and the P4 priority suggest the latter; the recent AW-3071 fix mfa locker windows suggests Windows is being actively maintained.

What did AW-3216-poc-keychain-bio conclude?

That branch — in-window biometrics on macOS via LocalAuthenticationView, plus resetAuthorizedContext across layers — touches the same Darwin subsystem. Its findings, particularly the “SE-key/Xcode wall” noted in commit 3407f48, likely bear on any further Darwin work. It was not analysed here.

Is there appetite for a format migration at all?

Several recommendations queue behind R-15. If the answer is no, the list collapses to documentation plus the Android one-liners.

Method. Static reading of every cryptographic path in packages/biometric_cipher plus the consuming layers in lib/security and lib/storage, cross-checked against Apple's SecKey.h from the locally installed MacOSX26.5.sdk, the Android Keystore contract, and the WinRT Windows.Security.Credentials / Windows.Security.Cryptography contracts. §08 additionally reads the ticket's declined pull request — adguard-wallet #112 at 9ebb87a, 27 commits across 164 files — from the Bitbucket API.

Not done. No code was executed, no device testing, no fuzzing, no side-channel analysis. Four items need confirmation on real hardware before being acted on: the exact failure mode of F-5 on API 23–27; the measured cost of the F-7 enclave keygen; Android auth-timeout semantics on API 28–29; and whether current Windows builds still return deterministic signatures across reboots and Hello re-authentication — the assumption the entire Windows backend rests on.
