ECIES, Byte by Byte

eciesEncryptionCofactorX963SHA256AESGCM is not a cipher. It is a recipe — five primitives in a fixed order, with every parameter already chosen for you. The name spells out the whole thing, if you know where to put the spaces.

The constant, decomposed
ECIESEncryptionCofactorX963SHA256AESGCM
ECIES Elliptic Curve Integrated Encryption Scheme. The umbrella construction: agree on a secret with a curve, then encrypt with a symmetric cipher. Everything that follows names one of its slots.
Encryption This constant is for SecKeyCreateEncryptedData / SecKeyCreateDecryptedData, not for signing or bare key exchange.
Cofactor Which flavour of ECDH. Multiply by the curve's cofactor h before the shared point is taken. On P-256, h = 1 — so this word changes nothing. Measured below.
X963 The key-derivation function. ANSI X9.63: hash the shared secret together with a counter and a context string, repeatedly, until you have enough bytes.
SHA256 The hash inside that KDF. (The family also offers SHA-1, 224, 384 and 512.)
AES The bulk cipher. Key length is not in the name — it is inferred from the curve. P-256 gives you AES-128, always.
GCM The mode. Authenticated: a 16-byte tag rides along, and the IV is sixteen zero bytes — which is the one design choice here worth arguing about.
asymmetric half — curve arithmetic and key agreement symmetric half — the cipher that moves the bytes
The problem it solves

A P-256 key cannot encrypt anything

This is the fact everything else follows from. RSA keys encrypt; elliptic-curve keys do not. An EC private key can sign, and it can agree on a secret with another EC key — that is the entire repertoire.

The Secure Enclave makes this concrete. It generates and holds exactly one kind of key — kSecAttrKeyTypeECSECPrimeRandom at 256 bits, i.e. NIST P-256 — and it will perform exactly two operations with it: ECDSA signing and ECDH key agreement. There is no RSA in there, and no encrypt verb at all.

So a wallet that wants to seal 32 bytes of master key behind Face ID has a gap to bridge: it holds a key that cannot encrypt, and it needs encryption. ECIES is that bridge, and it has a standard shape — a KEM that produces a fresh symmetric key out of curve arithmetic, feeding a DEM that does the actual encrypting.

The property that makes this the right shape for a wallet. Key agreement against a public key needs no private key and therefore no authentication. Sealing the master key costs no biometric prompt; only opening it does. That asymmetry is unique to the hybrid design — the symmetric Keystore design on Android prompts in both directions.

Encryption

Four stages, no parameters

Apple's header states the whole construction in six lines. Everything below is that paragraph, drawn out and then checked.

kSecKeyAlgorithmECIESEncryptionCofactorX963SHA256AESGCM
Legacy ECIES encryption or decryption, use kSecKeyAlgorithmECIESEncryptionCofactorVariableIVX963SHA256AESGCM in new code. Encryption is done using AES-GCM with key negotiated by kSecKeyAlgorithmECDHKeyExchangeCofactorX963SHA256. AES Key size is 128bit for EC keys <=256bit and 256bit for bigger EC keys. Ephemeral public key data is used as sharedInfo for KDF. AES-GCM uses 16 bytes long TAG and all-zero 16 byte long IV (initialization vector). MacOSX.sdk 26.5 · Security.framework · SecKey.h, lines 1152–1156

Stage 1 — a keypair that lives for one message

Every call to SecKeyCreateEncryptedData mints a fresh P-256 keypair (de, Qe) inside the Security framework. The private half is used once, for the next stage, and then destroyed; the public half is published in the clear at the front of the output.

This is what makes the scheme non-deterministic: encrypting the same plaintext twice under the same recipient key produces two entirely different blobs. It is also, as we will see, the single fact that rescues the all-zero IV.

Stage 2 — cofactor ECDH

Multiply the ephemeral private scalar by the enclave's public point (times the curve cofactor h), and take the x-coordinate of the result. That is Z, 32 bytes for P-256. The recipient can reproduce the same value from the opposite pair — ds against Qe — which is the entire trick of Diffie–Hellman.

Z is a shared secret but a poor key: it is a curve point coordinate, not uniformly random bytes, and it is identical for every message between the same two keys. Hence stage 3.

Stage 3 — ANSI X9.63, in full

X9.63 is the simplest respectable KDF there is: hash the secret with a big-endian counter and a context string, concatenate digests until you have enough bytes, truncate.

Two things about the sharedInfo slot are worth pausing on. First, it is the ephemeral public key — public, attacker-visible data, which is fine: a KDF's context input is meant to bind, not to hide. Second, because it changes every message, K changes every message even though Z would too. It is belt-and-braces domain separation, and it is the mechanism that ties a derived key to exactly one blob.

Stage 4 — AES-128-GCM, all-zero IV

K encrypts the payload with AES in Galois/Counter Mode, producing ciphertext the same length as the plaintext plus a 16-byte authentication tag. No additional authenticated data is passed. The IV is sixteen zero bytes, fixed, forever.

A detail most write-ups skip: GCM's native nonce is 96 bits. A 16-byte IV is a legal but non-native length, so the counter block J0 is derived by running the IV through GHASH rather than by simple concatenation. It makes no practical difference here — J0 is still a fixed value for a given key — but it is why a hand-rolled reimplementation that assumes a 12-byte nonce will not interoperate.

The output

81 bytes of overhead, and where they go

The result is one opaque Data. It is three concatenated fields with no header, no version byte and no algorithm identifier — the reader is expected to already know which constant produced it.

The 44-byte middle is not a coincidence. The plugin's Dart layer base64-encodes the 32-byte master key before handing it down, so the string that reaches SecKeyCreateEncryptedData is 44 ASCII characters. 65 + 44 + 16 = 125 bytes on disk, every time.

Decryption

The same derivation, run from the other side

Nothing about the key schedule is stored. Decryption re-derives K from scratch — which is why the blob has to carry Qe, and why tampering with those 65 bytes fails the tag check rather than producing garbage.

What that boundary does and does not buy you. An attacker who steals the blob and the device storage gets nothing: without the enclave they cannot compute Z. An attacker with code execution in the process at the moment of a successful unlock sees K and the master key in ordinary memory. The enclave protects the key at rest and gates its use; it does not protect the plaintext after the user has authorised its release. That is inherent to any design where the app needs the bytes.

Authentication is not optional

GCM's tag covers the ciphertext, and the KDF binding covers Qe, so every byte of the blob is effectively authenticated. Flipping a single bit anywhere — in the ephemeral key, the ciphertext or the tag — makes SecKeyCreateDecryptedData return nil rather than wrong plaintext. All three cases were tested; all three were rejected.

Verification

Rebuilt by hand, from the outside

A header comment is a claim, not evidence. So the pipeline above was reimplemented from scratch against a software P-256 key and checked against Apple's own output at every joint.

The test uses a software key rather than a Secure Enclave one for the obvious reason — the cross-check needs the private scalar available for an independent ECDH. The algorithm is identical either way; only the location of ds differs, and that location has no bearing on the byte format.

ANSI X9.63 KDF, reimplemented Swift · macOS 26.5 
func x963(_ z: Data, sharedInfo: Data, out: Int) -> Data {
    var result = Data(); var counter: UInt32 = 1
    while result.count < out {
        var block = z
        block.append(contentsOf: withUnsafeBytes(of: counter.bigEndian) { Array($0) })
        block.append(sharedInfo)                // = the 65-byte ephemeral public key
        var digest = [UInt8](repeating: 0, count: Int(CC_SHA256_DIGEST_LENGTH))
        block.withUnsafeBytes { _ = CC_SHA256($0.baseAddress, CC_LONG(block.count), &digest) }
        result.append(contentsOf: digest); counter += 1
    }
    return result.prefix(out)
}

Three things people get wrong

The parts that look alarming and the part that is

1. The all-zero IV is safe — for a reason that is one refactor deep

Reusing a nonce in GCM is the textbook catastrophe: two messages under the same (key, IV) pair leak P1 ⊕ P2 and, worse, hand the attacker enough structure to recover the GHASH subkey and forge tags at will. A hard-coded IV of sixteen zeros looks exactly like that mistake.

It is not, because the IV is only half the pair. Every message gets a brand-new ephemeral keypair, so every message gets a different K. The pair (K, IV) is unique even though IV is constant.

So it is safe as written, and fragile as a design. The invariant that protects it ("never reuse a derived key") lives nowhere in the code — it is a property of Apple's implementation that a future refactor cannot violate today, but a hand-rolled reimplementation easily could.

2. “Cofactor” is a no-op on this curve

The cofactor h of an elliptic curve is the ratio between the number of points on the curve and the order of the subgroup you actually use. Cofactor ECDH multiplies by h before taking the shared point, which kills small-subgroup attacks on curves where h > 1.

P-256 has h = 1. Multiplying by one is multiplying by one. The word in the constant name is doing no work — and this is testable: cofactor and standard ECDH produce identical shared secrets on P-256, and a blob sealed with eciesEncryptionStandardX963SHA256AESGCM opens cleanly with the Cofactor constant.

Which does not make the choice wrong — it makes it inert. Pick either; the naming just means one of them would still be correct if Apple ever shipped a Secure Enclave curve with a cofactor.

3. AES-128 is not a setting

This is the one that actually constrains the design. The header rule is “128bit for EC keys ≤ 256bit”, and the Secure Enclave supports exactly one curve: P-256. There is no larger key to move to, no parameter to pass, and no variant of the constant that asks for AES-256.

So a 256-bit master key ends up wrapped at 128-bit strength on this path. That is not a break — 128-bit symmetric security is far beyond reach — but it is a real asymmetry against the password path, which wraps the same key at its full width. Worth documenting; not worth an incident.

Migration

What “Legacy” actually changes

Apple's own header opens by telling you not to use this constant. The replacement, …CofactorVariableIVX963SHA256AESGCM, differs in exactly one place: it asks the KDF for 32 bytes instead of 16, and takes the IV from the second half.

That last row is the whole migration problem. The two formats are indistinguishable by length, so switching constants silently invalidates every stored blob — for this plugin, every enrolled user's biometric wrap. It is a one-word code change and a real migration: keep a version marker alongside the blob, try the new constant first, fall back to the old one, and re-wrap on the next successful unlock.

Priority, honestly. Nothing is exploitable today. The case for moving is that it deletes a fragile invariant, and that Apple will eventually stop carrying the legacy path. It belongs on a roadmap, not in a hotfix.

Context

One of twenty siblings

The constant sits in a small combinatorial family: two ECDH flavours × five hash functions × two IV strategies. Twenty names, one construction.

AxisOptionsWhat is in use, and why
ECDH flavour Standard · Cofactor Cofactor — indistinguishable from Standard on P-256, so the choice is stylistic
KDF hash SHA-1 · 224 · 256 · 384 · 512 SHA-256 — matched to the curve; a longer hash buys nothing when the request is 16 bytes
IV strategy Legacy · VariableIV Legacy — the one Apple recommends replacing

The plugin does not hard-code an assumption that any of these are available: before both encrypt and decrypt it calls SecKeyIsAlgorithmSupported and throws a typed error if the answer is no. That check is cheap and correct, and it is what a migration would hang off.

In one paragraph

The whole mechanism, restated

Generate a throwaway P-256 keypair. Multiply its private half against the Secure Enclave's public point to get a 32-byte shared secret. Hash that secret together with a counter and the throwaway public key, and keep the first 16 bytes of the digest as an AES-128 key. Encrypt the payload with AES-GCM under a fixed all-zero IV, safe because the key is never reused. Ship the throwaway public key, the ciphertext and the 16-byte tag as one 125-byte blob. To open it, hand the throwaway public key back to the enclave, pass a biometric check, and repeat the derivation from the other side.

Nothing in that sentence is configurable. The one word of it that carries a design decision is fixed, and the fix for that is a constant rename plus a migration.
