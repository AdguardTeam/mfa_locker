AW-3216/ packages/biometric_cipher/ Swift ↔ Dart wiring/ 27 Aug 2026

What the plugin must change for in-window Touch ID

A code-level trace of the AW-3216 prototype inside packages/biometric_cipher: whether the Swift is correct, whether Dart calls it correctly, how the biometric flow changes, and whether the change can stay inside Swift. The example/ app is out of scope — it is not adapted to the concept yet.

Correction after hardware verification (27 Aug, later the same day)

The first version of this page claimed a policy-authorized context would not satisfy the key's access control. That was wrong. Verified in the signed packages/biometric_cipher/example on macOS 15 with Touch ID: a context paired with LAAuthenticationView and authorized in-window by evaluatePolicy(.deviceOwnerAuthenticationWithBiometrics) is accepted by the Secure Enclave key — decrypt completes in 29–33 ms with no system sheet. After resetAuthorizedContext the sheet returns; cancel leaves state intact; a new in-window attempt is silent again.

The call the ticket proposed, evaluateAccessControl(.useKeyDecrypt), is the part that does not work: macOS returns LAError -1009 "Operation is not allowed" in ~10 ms, signed or unsigned, for any ACL flags (.useKeySign, .useItem and evaluatePolicy are all accepted). The branch's fail-soft was hiding a permanent failure, not a transient one. Sections below are annotated where the original text is superseded; the platform-contract, lifecycle and thread-safety findings stand.

Is the Swift correct?
Mechanism yes — lifecycle no
Pairing a context with the in-window view and reusing it after evaluatePolicy works (verified). The defects are around it: iOS build break, two unsynchronized writers, no invalidation, a dead .useKeyDecrypt path.
Does Dart call it correctly?
Mechanically yes, semantically no
Method names, channels and error codes line up. But the “no-op elsewhere” contract throws on three platforms, and the widget goes deaf after a cancel.
Can Swift alone do it?
Yes, for the mechanism
With the existing decrypt method channel unchanged — verified: 29 ms decrypt, no sheet. New Dart API is needed only for the UI surface and for lifecycle (cancel / lock).

1 · How the biometric flow changes

Today: one call, one system sheet, key op inside it

On master, biometrics on macOS are entirely implicit. Dart calls decrypt(tag, data); Swift builds a fresh LAContext, attaches it to the SecItemCopyMatching query, and the Secure Enclave's access control (.privateKeyUsage + .biometryCurrentSet) makes SecKeyCreateDecryptedData raise the system Touch ID sheet. That sheet is a separate window — the source of the focus bug in AW-3151.

The concept: authorize first, reuse the context

Both halves of this idea are present on the branch. What is missing is the connection between them, and that gap is the single correctness problem everything else hangs off.

2 · Swift correctness — the branch as it stands

Superseded by verification. This section's original premise — that only Path A yields a context the key accepts — was wrong. On hardware, Path B's policy credential is accepted (decrypt 29–33 ms, no sheet) and Path A's .useKeyDecrypt is refused outright (LAError -1009). The two-writers / last-writer-wins structural problem below is still real; the labels inside the figure should be read with A and B swapped.

Two writers, one slot, neither wired to the other

SecureEnclaveManager now has a single mutable slot, evaluatedContext, and two independent code paths fill it with no ordering, no synchronization, and no record of which one wrote last.

The SDK header for LAAuthenticationView — the AppKit view the SwiftUI LocalAuthenticationView wraps — still describes the right composition; it just lists both evaluations, and only one of them is usable for this key:

LAAuthenticationView.h: “The authentication is controlled using the provided authentication context. When evaluatePolicy or evaluateAccessControl is called on this context, the UI will be presented using this view rather than using the standard authentication alert.”

The view is a presentation route for a context, not an authenticator. Pair the context with the view, then drive the evaluation from the manager so that one owner decides what was authorized and when. The verified shape: 

// branch — BiometricInAppView.swift:86–92 (the view authenticates on its own; mechanically fine,
// but the manager never learns what happened except via a donated context)
LocalAuthenticationView("Continue with Touch ID",
    reason: Text("Unlock the wallet with biometrics"),  // runs evaluatePolicy inside
    context: context) { result in handler(result) }

// verified — pair only, then drive the evaluation from the manager (one owner)
let authView = LAAuthenticationView(context: context, controlSize: .large)   // AppKit, macOS 12+, pairs only

// SecureEnclaveManager.authorizeContext (background queue):
try AuthenticationManager.evaluateAccessControl(context, reason: authTitle)   // -1009 on macOS — dead end
try AuthenticationManager.requestBiometricAuthentication(context, reason: authTitle)  // evaluatePolicy — UI renders *in the view*
evaluatedContext = context                                                // decrypt reuses it: 29 ms, no sheet
Simpler still: LAAuthenticationView(context:controlSize:) is a public NSView available from macOS 12.0. A Flutter platform view can return it directly — no NSHostingView, no SwiftUI struct, no import of the underscored _LocalAuthentication_SwiftUI module, and a lower OS floor than the branch's 13.0.

3 · Dart → Swift call correctness

The plumbing is straight; the contract is not

Every Dart-side addition reaches its Swift counterpart. The method names match on both sides of the channel, the platform-view type string matches the registered factory id, the per-view event channel name is built identically, and every error code Swift can raise from the new handler already has a row in BiometricCipherExceptionCode.fromString.

The two contract breaks

  • “No-op elsewhere” is not true. MethodChannelBiometricCipher catches only PlatformException. On Android the handler's else → result.notImplemented() and on Windows MethodName::kNotImplemented surface as MissingPluginException, which propagates uncaught through BiometricCipher, BiometricCipherProviderImpl (also catches only BiometricCipherException) and SecurityProviderImpl. iOS does not reach this point — it fails to compile (see §5).
  • Cancel deafens the Dart widget but not the Swift view. _resolved latches on both onSuccess and onFailure and is never cleared. After a cancel, the next successful touch calls setAuthorizedContext in Swift while Dart drops the event. Dart thinks the app is still locked; Swift has an armed context that will make the next decrypt silent.

4 · Swift-only, or new Dart calls?

The mechanism needs no new Dart. The lifecycle does.

This is the question that decides the shape of AW-3289. Separate it into three concerns, because they have different answers.

What that means for the two methods the branch added

Added Dart APINeeded?Reasoning
evaluateBiometricPolicy() Only as a fallback With the in-window view driving evaluatePolicy on its paired context, an explicit pre-authorization call from Dart is redundant. It remains useful as the system-sheet fallback on macOS 11, or when no view is mounted — but it must stop calling .useKeyDecrypt (always -1009) and should return a result the app can branch on, not Void.
resetAuthorizedContext() Yes Swift has no way to observe Locker.lock(). Something must tell it to invalidate and drop the context, and this is that signal. It must call LAContext.invalidate(), not just nil the reference.
BiometricInAppView widget Yes The only way to put a native view in the widget tree. The onSuccess/onFailure event channel is right in shape; the one-shot latch must move to Swift, which owns the context.
SecurityProvider pass-throughs (locker) Reconsider SecurityProviderImpl now reaches around Locker to a second singleton for macOS-only calls. A cleaner seam is a single Locker-level hook (“biometric session ended”) that the locker invokes from its own lock(), so consumers cannot forget it.
The reuse window is a security decision, not an implementation detail. In this codebase every biometric operation is its own Secure Enclave decrypt — loadAllMeta, readValue, write, delete each call _getDecryptedMasterKey → cipherFunc.decrypt. On master that means one Touch ID per operation. A stored context that is never invalidated turns that into one Touch ID per process lifetime. Whether the desired behaviour is single-use (unlock only), a short TTL, or session-long is a product choice that should be written into AW-3289 before the code is.

5 · Swift defects, ranked

01

Unguarded macOS imports compile into the iOS target

Blocker
darwin/Classes/Views/BiometricInAppView.swift:1–5 · pubspec sharedDarwinSource: true · podspec Classes/**/*

import Cocoa, FlutterMacOS, _LocalAuthentication_SwiftUI sit above the #if os(macOS). Reproduced with swiftc -sdk iphoneos -typecheck: no such module 'Cocoa'. Violates the ticket's AC “iOS не сломана”.

Fix: imports inside the guard; drop the underscored module (the cross-import overlay makes LocalAuthentication + SwiftUI sufficient), or drop SwiftUI entirely in favour of LAAuthenticationView.
02

.useKeyDecrypt never works; fail-soft hides a permanent failure

Blocker
SecureEnclaveManager.swift:152–174 · AuthenticationManager.swift:105–137 · commit bff5b4d

(Replaces the original finding 02, which claimed the in-window policy credential would be rejected — disproved on hardware.) evaluateBiometricPolicy calls evaluateAccessControl(.useKeyDecrypt), which macOS refuses with LAError -1009 every time, in ~10 ms. The fail-soft added in bff5b4d ("can fail transiently … cold start") swallows this, so the method silently does nothing and every unlock falls through to the system sheet — the exact behaviour the ticket set out to remove.

Fix: drop the .useKeyDecrypt attempt; authorize with evaluatePolicy(.deviceOwnerAuthenticationWithBiometrics) on a context paired with the in-window view; return a result instead of swallowing errors.
03

Context is never invalidated; reset is cosmetic

Security
SecureEnclaveManager.swift:186–190 · BiometricInAppView.swift:38

resetAuthorizedContext() sets the slot to nil. LAContext.invalidate() is never called. The view holds the same context strongly and can re-donate it. While the slot is set, every decrypt(tag:) for any tag skips biometrics.

Fix: invalidate() on reset and in the view's deinit; consume-on-use or TTL; and do not reuse the context across tags — bind it to the tag it was authorized for.
04

Unsynchronized cross-thread access to evaluatedContext

Correctness
written on main (platform-view callback) · read on DispatchQueue.global(.userInitiated) (decrypt, evaluateBiometricPolicy)

No queue, lock, or actor. A data race today; a compile error under Swift 6 strict concurrency.

Fix: a serial queue owned by the manager, or make the manager an actor.
05

Unbounded semaphore wait behind a control with no Cancel

Correctness
AuthenticationManager.swift:119–125 (evaluateAccessControl)

Copies the existing requestBiometricAuthentication pattern, but the in-window control has no Cancel button. A userInitiated thread parks indefinitely waiting for a touch; on the main thread it deadlocks.

Fix: withCheckedThrowingContinuation and async, or a bounded wait that reports a timeout.
06

Fail-soft returns Void and hides which path will run

Design
SecureEnclaveManager.swift:152–174

Every non-cancel error is swallowed — lockout, system cancel, app cancel, user fallback. The caller cannot tell “pre-authorized, decrypt is silent” from “decrypt will prompt”. guard authTitle != nil also makes a missing configure() a silent success, leaving authTitle ?? "…" as dead code.

Fix: return .authorized / .willPrompt / .canceled; throw invalidAuthTitle when unconfigured.
07

Protocol and mock drift

Design
SecureEnclaveManagerProtocol.swift · LAContextProtocol.swift · example/shared_native_test/Mocks/MockLAContext.swift · test/mock_biometric_cipher_platform.dart
  • SecureEnclaveManagerProtocol has a non-mutating setter but no : AnyObject constraint — the factory's existential copy would be wrong for a value-type conformer.
  • evaluateAccessControl added to LAContextProtocol; MockLAContext does not implement it — native test target no longer conforms.
  • Two methods added to BiometricCipherPlatform; the Dart mock is not updated — flutter analyze --fatal-infos errors and the plugin test suite fails to load.
  • BiometricCipherPlugin.secureEnclaveManager widened from private let to private(set) var only to reach it during registration. Build the factory in init.
  • No deinit on BiometricInAppView: handler not torn down, context not invalidated.

6 · Recommended shape for AW-3289

One owner, one authorization, one signal

  1. Mechanism — proven. Pair a context with LAAuthenticationView, evaluatePolicy(.deviceOwnerAuthenticationWithBiometrics) on it from the manager, store on success, reuse in getPrivateKey: decrypt in 29–33 ms with no sheet in the signed example. Remove every .useKeyDecrypt call — it is a guaranteed -1009.
  2. Move the one-shot to Swift. The manager owns the context; it should own the “already resolved” state too. Dart's _resolved goes away.
  3. Make resetAuthorizedContext mean invalidate(), and have Locker.lock() call it rather than trusting every consumer to remember.
  4. Bind the authorization to a tag. getPrivateKey(tag:) should reuse the context only for the tag it was authorized against.
  5. Return a result from evaluateBiometricPolicy, keep it as the macOS-11 / no-view fallback, and stop swallowing errors.
  6. Fix the platform contract: guard the imports, make “no-op elsewhere” true in Dart (platform check, or catch MissingPluginException), update both mocks, and get analyze + tests green before anything else lands.
