AdGuard Wallet · Encryption Architecture Review

How four operating systems guard one master key

AdGuard Wallet locks every seed phrase behind a single master key, and lets a device's own secure hardware unwrap it with a fingerprint or face instead of a password. The Dart-level scheme is identical everywhere. What each OS actually lets an app bind that key to is not — and on one platform, that gap turned into a real vulnerability.

Ticket Jira AW-321 Historical PR Bitbucket #112 · declined Library locker v1.0.6 / biometric_cipher · AdguardTeam/mfa_locker Reviewed August 2026

01 — Where this stands today

The ticket, and what actually shipped instead

AW-321 asked, in December 2024, for an iOS/macOS implementation combining asymmetric and symmetric cryptography via the Secure Enclave. The resulting branch became PR #112, a new secure_mnemonic plugin with hand-rolled, per-platform Swift managers — SecureEnclaveManager.swift for iOS, a separate GenerateKeyPairExtension.swift for macOS, and Android/Windows stubs that never grew past Flutter's plugin template. Bitbucket declined the PR in February 2025; the ticket has sat in To Do ever since, with a 2025 comment simply asking whether the approach is still worth pursuing.

It was overtaken by a broader initiative. locker (a.k.a. MFA Locker) is a standalone, source-available library at github.com/AdguardTeam/mfa_locker, pulled into the wallet as a git dependency and already wired into every screen that touches wallet secrets. It solves AW-321's actual problem — hardware-backed biometric unlock — for all four desktop/mobile targets at once, through one shared plugin, biometric_cipher. AW-321 is functionally superseded, just not by the branch anyone was watching.

02 — The shared foundation

One envelope, wrapped four different ways

Every platform runs identical Dart code for the data itself (package:locker, using package:cryptography): a random 256-bit master key encrypts every vault entry with AES-256-GCM; the password path derives its own key with Argon2id at OWASP's recommended parameters (19 MiB memory, 2 iterations); an HMAC-SHA256 tag over the whole store catches tampering. The master key itself is never derived twice — it's generated once and stored as a list of KeyWraps, one per unlock method (Origin.pwd, Origin.bio), so the password and the biometric prompt are two independent doors onto the exact same key.

master key (AES-256, random)
├── wrapped by Argon2id(password)  —  same on every platform
└── wrapped by biometric_cipher(tag)  —  this is where the four platforms diverge

Only that second wrap is platform-native code. It's the entire surface of this report.

03 — Platform

Android

Sound design, real code defects

Android's biometric key is a symmetric AES-256 key generated straight into the Android Keystore and gated by androidx.biometric.BiometricPrompt. The design is correct and the historical failure modes from the pre-biometric_cipher era are gone — but the code has accumulated a handful of real bugs, none of them exploitable, all of them worth fixing.

Key generator
KeyGenerator("AES", "AndroidKeyStore")
Cipher transform
AES/GCM/NoPadding
Auth requirement
setUserAuthenticationRequired(true), timeout 0 — every op re-prompts
Hardware tier
setIsStrongBoxBacked() called unconditionally

What's solid

A real CryptoObject binds the cipher to the prompt (repositories/AuthenticationRepositoryImpl.kt:84), and cancel is cleanly split from genuine failure — ERROR_USER_CANCELED / ERROR_NEGATIVE_BUTTON map to authenticationUserCanceled, everything else to authenticationError. That's exactly the distinction a 2025 review comment on the old secure_mnemonic plugin asked for and never got. KeyPermanentlyInvalidatedException is caught before the biometric prompt ever shows, and the historical "second failed fingerprint crashes the app" bug (reported against the pre-decessor plugin under AW-300) has no equivalent path here — each callback fires exactly once and resumes the coroutine exactly once.

Findings

  • Defect

    StrongBox is requested unconditionally on a minSdk that predates it

    setIsStrongBoxBacked() requires API 28+, called with no SDK guard in SecureRepositoryImpl.kt:44, while build.gradle sets minSdk 23. On real API 23–27 devices this throws NoSuchMethodError — the method only carries a @RequiresApi lint annotation, nothing enforced at runtime.

  • Defect

    No StrongBox-unavailable fallback

    Android's documented pattern is try-StrongBox, catch StrongBoxUnavailableException, retry without it — some devices report the feature but fail generation anyway. That retry doesn't exist here, and the uncaught exception surfaces as the operation name (e.g. "generateKey") rather than a real BiometricCipherExceptionCode, because the handler falls back to that when the thrown type isn't one of the plugin's own sealed exceptions.

  • Dead code

    TPM status detection is hardcoded

    getTPMStatus() always returns SUPPORTED (SecureServiceImpl.kt:13) — no device check at all. UNSUPPORTED and TPM_VERSION_UNSUPPORTED are unreachable values.

  • Code defect

    A copy-paste error empties the configuration-error hierarchy

    All four nested subclasses meant for ConfigureException instead extend CryptographicException — it compiles (both are sealed in the same package) but leaves ConfigureException with zero real subclasses.

  • Gap

    Prompt isn't dismissed on external cancellation

    There's no invokeOnCancellation { biometricPrompt.cancelAuthentication() }. If the owning coroutine scope is cancelled while a system dialog is showing, that dialog is left on screen.

Test coverage: solid on unit logic (Robolectric + mocks); the one instrumented test needing a real biometric interaction is @Ignored, and nothing exercises the StrongBox-fallback or lockout paths above.

03 — Platform

Windows

Critical finding · feature disabled

This is the one platform where the biometric path was a genuine, exploitable vulnerability — not a coding slip, but a direct consequence of what Windows Hello can and can't promise to an ordinary desktop app. AdGuard's own security investigation (ticket AW-2956) is unusually thorough, and it now fully governs the shipped behavior.

How it worked

The plugin signed a fixed string with a Windows Hello credential and turned the signature into an AES key: KeyCredentialManager.OpenAsync(tag) → RequestSignAsync(data) → CreateAESKey(signature). That's a structurally different pattern from Apple's or Android's — sign-then-derive, not encrypt-then-store — and both inputs were constants baked into every build:

tag = 'adguard_wallet_bio_key'  (LockerConstants, identical on every install)
data-to-sign = 'locker_authentication_request'  (default, wallet never overrides it)

Same credential, same input, same signature every time — which is required for the key to be reproducible at every unlock, but also means the resulting AES key is fully determined by two non-secret, world-known strings.

Why this is Windows-only

On iOS, macOS and Android, the OS checks which app owns a hardware key before any biometric prompt appears — Apple via code-signing identity and Secure Enclave/keychain ownership, Android via the kernel UID enforced by the keystore daemon. Neither lets a second app touch the first app's key, biometric approval or not.

An unpackaged Win32 app — what Flutter for Windows produces — gets no equivalent. KeyCredentialManager exposes only a string name, scoped to the Windows user account, not the calling process. Any other program running as that same user can call OpenAsync('adguard_wallet_bio_key') and RequestSignAsync('locker_authentication_request') itself. The genuine system Hello prompt appears — it just never says which app asked. One careless approval and the malicious process holds the same AES key the wallet does, which unwraps the master key, which decrypts every seed phrase plus the raw database encryption key.

Two proposed fixes, both rejected

Package as MSIX, scope by Package Family Name — the ticket's original hypothesis, refuted with high confidence. A packaged-but-not-isolated app still runs full-trust; Microsoft's own guidance and community testing show credentials shared across PFNs at the user level regardless. Only a genuine AppContainer sandbox might change this, and that path is public-preview, Windows 11 24H2-only, has no first-class Flutter packaging route, and puts every native plugin at risk — flutter_secure_storage's DPAPI-keyed storage re-binds identity inside a container and can lock users out, and file-picker dialogs are a confirmed Microsoft won't-fix E_ACCESSDENIED in partial trust. The investigation's verdict: run a 1–3 day isolation experiment before spending anything on it, because the security benefit is still unproven.

Split the master key — derive half from the password, half from a Windows Hello-gated DPAPI secret. A formal review of this proposal found it doesn't fix the actual threat: UserConsentVerifier only returns an enum, it releases no key material and signs nothing, so malware simply skips calling it; and CryptProtectData/CryptUnprotectData are scoped to the user account, not the app — the exact mechanism behind Bitwarden's CVE-2023-27706. Stripped of both non-barriers, the scheme's security reduces to the password alone, with a biometric gesture bolted on for show.

03 — Platform

macOS

Shares iOS's code · one hardware gap

macOS doesn't have its own crypto implementation at all — pubspec.yaml sets sharedDarwinSource: true for both Apple platforms, and Flutter's tooling routes both straight to the same darwin/Classes Swift sources. The one plugin-level file remaining under macos/ is a vestigial podspec left over from before the platforms were unified; it isn't built.

Key type
Secure Enclave EC P-256, non-extractable private key
Cipher
.eciesEncryptionCofactorX963SHA256AESGCM
Access control
.biometryCurrentSet — auto-invalidates on re-enrollment
Hardware requirement
Apple Silicon or T2 — live-probed, no fallback

The single deliberate divergence from iOS is UX, not security: macOS skips the extra explicit confirmation prompt that iOS shows during key generation, on the reasoning that it's a redundant second Touch ID window on a Mac. Every other code path — encryption, decryption, key invalidation, deletion — is unconditional, shared Swift.

Findings

  • Hardware gap

    No software fallback on Macs without a Secure Enclave

    isSecureEnclaveSupported() does a live probe (attempts to create a temporary Secure Enclave key); on an Intel Mac without a T2 chip, that fails and every biometric operation surfaces secureEnclaveUnavailable. There's no software-only key path underneath it — biometric unlock is simply unavailable on that hardware class, the same way it now is on Windows, just for a hardware reason rather than a security one.

  • Hardening, already applied

    A macOS-specific Keychain quirk is explicitly worked around

    A comment in SecureEnclaveManager.swift documents that invalidated Secure Enclave keys can remain in the macOS Keychain reporting errSecInteractionNotAllowed — indistinguishable from a valid key by that status alone. isKeyValid cross-checks against a tracked enrollment-state baseline to catch this, unconditionally on both platforms. It traces to two dedicated fixes in the commit history (AW-2524, AW-2526), so this reads as hardening earned from a real bug, not speculative defense.

03 — Platform

iOS

Cleanest implementation of the four

This is the platform AW-321 originally asked for, and — via the shared darwin code described under macOS — it's what actually got built: a real asymmetric-plus-symmetric hybrid through the Secure Enclave, using Apple's own ECIES suite instead of the bespoke ECDH/HKDF/AES-GCM code the declined PR #112 hand-rolled.

Key generation
kSecAttrKeyTypeECSECPrimeRandom, 256-bit, kSecAttrTokenIDSecureEnclave
Encrypt / decrypt

Under the hood
Ephemeral EC key · cofactor ECDH · X9.63-SHA256 KDF · AES-GCM
Access control
.privateKeyUsage + .biometryCurrentSet (falls back to .userPresence only if biometry is unavailable)

Every biometric decrypt runs through the Security framework's own access-control check — Face ID or Touch ID triggers implicitly inside SecKeyCreateDecryptedData, with no bespoke prompt-handling code to get wrong. .biometryCurrentSet (never the looser .biometryAny) means the key auto-invalidates the moment a new fingerprint or face is enrolled — the stricter, safer choice. isKeyValid is a genuine silent probe: it queries with kSecUseAuthenticationUISkip set explicitly, so checking key validity can never accidentally trigger a Face ID prompt.

One behavioral extra

iOS alone shows an explicit confirmation prompt during key generation (skipped on macOS — see above), with a clean rollback: if the user cancels, the partially-created key is deleted via a best-effort try? deleteKey(tag:). No TODOs or open issues were found anywhere in the shared darwin/Classes source.

04 — Synthesis

What actually differs, and why

Three different cryptographic shapes, not four

iOS and macOS run one true asymmetric-plus-symmetric hybrid (Secure Enclave EC keypair, unwrapped via ECIES) — literally the same Swift files. Android runs a plain symmetric AES key inside the Keystore; simpler, and entirely adequate given Android's UID-level app binding. Windows, while it worked, wasn't encryption-shaped at all: it turned a deterministic signature into a key, a structurally different — and here, exploitable — pattern.

The real fault line is app-identity binding, not cryptography

Every platform here uses hardware that's individually strong: Secure Enclave, Android's TEE/StrongBox, Windows Hello's biometric matcher are all sound in isolation. What separates the safe platforms from Windows is a single OS-level guarantee: does the platform check which app is asking before it hands over a key, and does it do that check before showing any biometric prompt? Apple and Android both answer yes, unconditionally. Unpackaged Win32 has no such primitive — that's a platform limitation this codebase inherited, not a bug it introduced.

Code quality bugs cluster on Android

The Android implementation is the only one with defects independent of the vulnerability story above — the unguarded StrongBox call on old minSdk, the missing StrongBox-fallback retry, hardcoded TPM detection, the copy-paste exception hierarchy. None rise to the severity of the Windows finding, but they're concrete, fixable, and currently untested.

AW-321 is stale, not wrong

The ticket's premise — combine asymmetric and symmetric cryptography via the Secure Enclave — is precisely what shipped on iOS and macOS. It just shipped through biometric_cipher/locker, a cross-platform initiative the ticket never points to, while the branch it does point to (PR #112) sits declined. Worth closing AW-321 with a pointer to this architecture rather than leaving it open as unstarted work.
