biometric_cipher · Secure Enclave · ECIES

If we encrypt twice with the same public key, do we get the same AES key twice?

No. A brand-new AES key is derived on every single encrypt() call, because the public key is only half of the recipe — the other half is a fresh ephemeral key pair that SecKeyCreateEncryptedData generates internally each time and destroys before it returns.
And nothing extra needs to be stored for decryption: the ephemeral public key travels inside the ciphertext blob. The Secure Enclave holds exactly one secret — the same private key d, forever — and recomputes each message’s AES key on the fly.

Both of your intuitions were half right: the keys are different every time, and decryption does need per-message material — but that material is public, so it rides along with the ciphertext instead of living in the enclave. The four steps below walk through exactly how, using the code in SecureEnclaveManager.swift.

FIRST

What the algorithm name actually promises

You remembered correctly: the code uses the older, “legacy” variant. SecureEnclaveManager.swift lines 147 and 167 both select .eciesEncryptionCofactorX963SHA256AESGCM — Apple’s SecKey.h marks it Legacy and points new code at the …VariableIV… sibling. What “legacy” changes is covered in step 4; it does not change the answer to your question.

eciesEncryptionCofactorX963SHA256AESGCM

ecies
Elliptic Curve Integrated Encryption Scheme — a bundle: key agreement + key derivation + symmetric cipher in one call.
Cofactor
the ECDH flavour. On P-256 the cofactor is 1, so this is a no-op distinction here.
X963SHA256
the KDF: ANSI X9.63 with SHA-256 turns the raw ECDH result into a clean AES key.
AESGCM
the actual data cipher: AES-128-GCM (128-bit, because the Secure Enclave key is a 256-bit EC key).

The important word is Integrated. A P-256 key cannot encrypt your data directly — EC keys only do point arithmetic. So “encrypting with the public key” really means: agree on a fresh symmetric key using EC math, then encrypt with AES. The agreement step is where the randomness lives.

STEP 1

One encrypt call, end to end

When encrypt() hands the plaintext to SecKeyCreateEncryptedData, the Security framework silently generates a one-shot ephemeral key pair (e, E) — a fresh random private scalar e and its public point E. The AES key is not derived from your public key alone; it is derived from the ECDH combination of e (new every call) with your enclave public key P (always the same). Fresh e in, fresh K out.

Note what happens to the two ephemeral halves. The private scalar e exists for microseconds — used once for the ECDH multiply, then gone; it is never written anywhere. The public point E is deliberately published: it becomes the first 65 bytes of the blob your code stores. That asymmetry is the entire trick.

STEP 2

Run it twice — same P, different everything else

Because e is drawn fresh from the system RNG on every call, two encryptions of even the same plaintext under the same public key agree on nothing downstream: different shared secret, different AES key, different ciphertext, different blob. You can verify this from Dart in seconds — call encrypt() twice with one string and compare the Base64: the outputs differ from the first byte of the ephemeral key onward.

Why your feared scenario would be catastrophic

Your instinct was sound. If the AES key really were a pure function of P, every message would be encrypted under the same (key, IV) pair — and this algorithm uses an all-zero IV. Reusing a key+nonce pair in GCM leaks the XOR of plaintexts and can forge tags: a real break, no enclave needed. The scheme is safe precisely because that scenario never occurs — the fresh ephemeral key guarantees a unique AES key per message.

STEP 3

Decryption: the same key, recomputed from the other side

So how does decrypt() find a key that was never stored? It doesn’t look it up — it re-derives it. The blob opens with E, and Diffie–Hellman symmetry means the enclave’s private key d combined with E lands on the same shared secret the encryptor reached from the opposite pair of halves. Same secret → same KDF → same K.

The answer to your second question

Different keys per message do not require storing anything per message. The “secret” each message needs is reconstructed from two parts: one public and attached to the message (E), one private and permanent (d in the enclave). One stored key decrypts an unlimited number of blobs, each wrapped under its own AES key.

A pleasant side effect of this design, and the reason the plugin can re-wrap data silently: encryption uses only public material, so encrypt() never shows a biometric prompt. Face ID appears only on decrypt(), when d must actually be used.

STEP 4

What an attacker holds, and why it isn’t enough

Suppose an attacker exfiltrates everything your app can see on disk and in memory after the fact. Their haul:

P — public the enclave public key. Public by design; grants the ability to encrypt, which helps no one.
E — public the ephemeral public key, first 65 bytes of every blob. Also useless alone — it is the public half.
blob ciphertext + tag. Opaque without K.
e — needed the ephemeral private scalar. Destroyed microseconds after key derivation; it never existed outside that one call’s stack.
d — needed the enclave private key. Generated inside the Secure Enclave, marked non-exportable, and usable only after Face ID / Touch ID (.biometryCurrentSet).

Recovering K means computing the shared secret S from P and E alone — with neither private half. That is the computational Diffie–Hellman problem on P-256, and it is exactly the hardness assumption all of TLS rests on. There is no shortcut through the KDF either: X9.63/SHA-256 is deterministic, but its input is the secret the attacker doesn’t have. So the honest phrasing of your first question is: the AES key is not “derived from the public key” — it is derived from a Diffie–Hellman agreement in which the public key is the only reusable ingredient, and every derivation consumes one private value that no longer exists and one that never leaves silicon.

FINALLY

The “older version” you remembered — what it actually changes

Legacy vs VariableIV (finding F-8 in the crypto analysis)

The variant in the code derives 16 bytes from the KDF (just the AES key) and uses a fixed all-zero IV. The modern eciesEncryptionCofactorVariableIVX963SHA256AESGCM derives 32 bytes — key and IV. With a unique key per message the zero IV is harmless, which is why Apple shipped it at all. But it is one refactor away from danger (if anyone ever caches or reuses a derived key, step 2’s red box becomes reality), so migrating is right on principle. Note it is format-breaking: old blobs will not decrypt under the new constant, so a migration needs a version byte in the stored format.

One more inherent quirk worth knowing: because the Secure Enclave only holds 256-bit EC keys, ECIES here always yields AES-128-GCM — there is no parameter to request AES-256. So the biometric wrap of the AES-256 master key is itself protected at the 128-bit level. Not broken, not urgent, but a real asymmetry with the password path that deserves a line of documentation.
