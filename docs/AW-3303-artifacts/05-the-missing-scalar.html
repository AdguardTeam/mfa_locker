The Missing Scalar

The header says the AES key is negotiated using the public key. It never says derived from the public key — and the difference is one secret number that exists for a few microseconds and is never written down.

The objection

“The symmetric key is generated from the public key. The public key is public. So anyone can regenerate the symmetric key and decrypt the blob.”

The correction

The key is generated from a secret scalar multiplied by a public point. There are exactly two (scalar, point) pairs that reach it — the sender's and the enclave's — and every party who holds only public data holds two points and no scalar. Two points cannot be multiplied together.

Notation

Three kinds of symbol, one operation

Everything below is written in terms of integers called scalars (d), points on the curve (Q), and one fixed point everybody shares (G). A public key is what you get when you multiply G by your scalar; that multiplication is the only operation the whole scheme uses.

k·G means "add G to itself k times" under the curve's point-addition rule. It is computed by double-and-add — about 256 doublings and additions — not by k separate steps. Going forward from a scalar to a point is cheap; going back from a point to the scalar that produced it is the discrete-log problem.

One consequence of "multiplication is repeated addition" is that the scalars commute. Adding G to itself ds times and then repeating that de times is adding G to itself de·ds times, in whichever order you like:

de · Qs  =  de · (ds · G)  =  (de · ds) · G  =  ds · (de · G)  =  ds · Qe

That identity is the whole reason two parties can land on the same point without either learning the other's scalar — and it is the identity the next section draws.

The mechanism

Two roads to Z, and neither one is paved with public data

Start from what the sender actually does. Before it touches the enclave's public key Qs at all, it draws a random 256-bit number de — a fresh secret that nobody else has ever seen. Then it computes one product on the curve:

Z  =  de · Qs

That is where the confidentiality comes from. Qs is public, yes — but Z is not a function of Qs alone; it is a function of Qs and de, and de is known to precisely one process for precisely one call.

The enclave reaches the same Z from the other side, because Qs = ds·G and Qe = de·G, so de·Qs = de·ds·G = ds·Qe. Each side multiplies its own secret by the other side's public point. Nobody ever multiplies two public points, because on an elliptic curve that operation does not exist.

Where the phrase “from the public key” comes from. The Security framework API is SecKeyCreateEncryptedData(publicKey, …): the only key you hand it is Qs. So documentation says the key is negotiated “with the public key”. The random de is an internal detail the API never shows you, which is why the sentence reads as if Qs were the sole input.

The ephemeral secret

A number that exists for one multiplication

The whole scheme rests on de being unavailable afterwards, so it is worth being precise about its lifetime. It is generated inside SecKeyCreateEncryptedData, used twice — once to make Qe, once to make Z — and then discarded. It is not returned to the caller, not written to the keychain, and not placed in the blob. What goes in the blob is Qe = de·G, which is a one-way image of it.

The half that is true

Anyone can make a key. Nobody can remake the key.

Here is the part of the intuition that is correct, and it is important not to lose it: with Qs in hand, anyone can run the sender's side of Fig 1. Draw a fresh de′, multiply, derive K′, encrypt. No enclave, no biometric, no permission.

That is not a weakness. That is the definition of public-key encryption — the public key is an open padlock, and anyone may snap it shut on a box. The plugin relies on exactly this: sealing the master key costs no Face ID prompt because sealing needs no secret from the recipient.

What the attacker wants is different. They do not want to seal a new box; they want to open a specific one that already exists. That box was locked under K, and K came from a de that the attacker never had and that no longer exists anywhere. Their fresh de′ gives them a fresh K′ — a different key, useless against the old ciphertext.

Reading the KDF line correctly

Qe goes into the hash — as a label, not as a secret

One more sentence in the sibling note may have fed the objection: “the ephemeral public key is used as sharedInfo for the KDF.” So a public value is an input to the key derivation. But look at the full hash input:

K = SHA-256( Z ‖ 00000001 ‖ Qe )[0..16]

All of the entropy the attacker lacks is in Z. Qe is there to bind the key to this particular blob — so that a Qe from one blob cannot be spliced onto the ciphertext of another — not to hide anything. A KDF's context string is meant to be public. If you deleted Qe from that line the scheme would lose a binding property but not one bit of confidentiality; if you deleted Z it would lose everything.

When the objection would be right. Your reading is exactly the failure mode to keep watching for. K becomes recoverable from public data if any of these ever happen: an implementation logs or caches de; de is drawn from a weak RNG (then Qe → de stops being hard); or the enclave's ds becomes extractable. None of those are properties of the algorithm — they are properties of the code around it, which is where review attention belongs.

In one paragraph

The whole answer, restated

The symmetric key is not derived from the public key. It is derived from a secret scalar times a public point. The sender's scalar is random, used once, and destroyed; the enclave's scalar never leaves the hardware. The attacker inherits the two public points and neither scalar, and turning two points into the secret they share is the Diffie–Hellman problem that P-256 is chosen to make infeasible. Anyone can use the public key to make a new key and seal a new message — that is what “public-key encryption” means — but nobody without one of the two scalars can reproduce the key that sealed an existing one.
