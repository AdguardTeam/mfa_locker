# Windows Hello: ресерч для безопасного хранения ключей кошелька

## Ресерч с использованием Windows Hello

Приложения типа 1Password и Bitwarden используют `UserConsentVerifier.RequestVerificationAsync(String)` — метод, который убеждается, что за текущей авторизацией стоит именно пользователь, и возвращает enum с результатом (аппрув или нет). По факту они завязываются только на факт прохождения верификации, а логика работы с данными находится исключительно в самом приложении. Windows Hello используется только на старте сессии при разблокировке приложения.

Один из вариантов, подтверждённых как жизнеспособный в нескольких ответах, — разделять мастер-ключ на две части. При входе в приложение всегда запрашивать пароль, из него выводить первую часть мастер-ключа и держать её в памяти короткое время (5 минут); в это время можно использовать Windows Hello для получения второй части. По истечении времени первая часть удаляется из памяти, и цикл повторяется с вводом пароля. Проблема этого подхода: часть ключа хранится в памяти — если есть возможность получить к ней доступ, достать вторую часть не составит труда, поскольку можно вызвать такое же окно верификации, как у приложения.

## Ресерч приложений-кошельков под Windows

Проверены следующие приложения: Trezor Suite, Dione, Guarda, Electrum, Now Wallet.

**Trezor Suite** использует `UserConsentVerifier.RequestVerificationAsync(String)` для авторизации пользователя в приложении. Сама работа с подписью транзакций и сид-фразой завязана на их аппаратном устройстве (флешке), которое работает офлайн и подключается к приложению отдельно.

**Dione** — на сайте описан функционал шифрования через Windows Hello, однако приложение удалено для скачивания повсеместно.

**Guarda**, **Electrum** и **Now Wallet** — Windows Hello отсутствует.

## Подход с разделением ключа на 2 части

Используемые термины:

- `UserConsentVerifier` — Windows API, который запрашивает у пользователя подтверждение личности (через Windows Hello: PIN, отпечаток, лицо) и возвращает результат верификации. Сам по себе не хранит и не шифрует данные — только подтверждает факт присутствия пользователя.
- `CryptUnprotectData` — Windows DPAPI функция для расшифровки данных, зашифрованных через `CryptProtectData`. Привязана к учётной записи пользователя и устройству — расшифровать можно только на том же компьютере и под той же учёткой.
- `device_secret` — секрет, сгенерированный с привязкой к конкретному устройству через DPAPI. Хранится в зашифрованном виде и доступен только после прохождения `UserConsentVerifier`.
- `password_key` — ключ, выведенный из пароля пользователя (например, через KDF вроде PBKDF2 или Argon2).
- `KEK` (Key Encryption Key) — ключ шифрования ключа. Получается из комбинации `password_key` и `device_secret`, используется только для расшифровки DEK.
- `DEK` (Data Encryption Key) — ключ шифрования данных. Непосредственно шифрует сид-фразу. Хранится в зашифрованном виде, расшифровывается через KEK только на время операции.

Сценарий работает следующим образом:

1. Пользователь вводит пароль (его можно сохранить и использовать позднее неопределённое время).
2. Приложение получает ключ из пароля (`password_key`).
3. Приложение вызывает `UserConsentVerifier`.
4. Если результат — Verified, приложение вызывает `CryptUnprotectData`.
5. Получает `device_secret` — значение, сгенерированное с привязкой к устройству.
6. Смешивает `password_key` + `device_secret`.
7. Получает KEK (ключ шифрования DEK).
8. Расшифровывает DEK (ключ шифрования сид-фразы).
9. Расшифровывает seed phrase только на время операции.

## Вывод

На текущий момент единственным рабочим методом остаётся описанный выше подход с разделением ключа на две части. Других проверенных вариантов нет. Можно искать альтернативные подходы, но они будут производными этой схемы — так или иначе сводиться к разделению секрета и совмещению частей после прохождения верификации.
