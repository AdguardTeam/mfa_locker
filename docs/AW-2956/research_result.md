## 1. Что удалось выяснить
Основной вывод: для обычного неупакованного Win32-приложения KeyCredentialManager, судя по полученным ответам, работает в границе пользователя и устройства, а не в границе конкретного исполняемого файла. Это значит, что Windows Hello подтверждает действие пользователя на этом устройстве, но не дает явной гарантии, что запрос пришел именно от приложения, которое создало credential. Возможность другого процесса того же пользователя открыть credential по известному имени выглядит не как обход биометрии, а как следствие модели доступа Windows для обычных Win32-процессов.
## 2. Суть атаки
Приложение хранит локальные секреты в зашифрованном виде. Доступ к ним завязан на мастер-ключ, а один из способов разблокировки мастер-ключа использует Windows Hello через KeyCredentialManager. Если вредоносный процесс запущен от имени того же пользователя и знает или находит имя credential, он может вызвать KeyCredentialManager.OpenAsync, показать системное окно Windows Hello и дождаться подтверждения пользователя. Если пользователь подтверждает запрос, вредоносный процесс может выполнить криптографическую операцию через тот же credential. В архитектуре, где результат этой операции позволяет открыть мастер-ключ, это может привести к расшифровке локального хранилища.
## 3. Что не решает проблему полностью
Скрытие имени credential не является полноценной защитой, потому что имя credential нужно считать идентификатором, а не секретом. Случайное имя может усложнить атаку, но не закрывает корень проблемы. TPM также не решает этот сценарий: он защищает ключевой материал от извлечения, но не отличает легитимный запрос приложения от запроса другого процесса того же пользователя, если пользователь подтвердил Windows Hello. Дополнительное окно внутри приложения перед вызовом Windows Hello тоже не закрывает проблему. Злоумышленник может запустить свое приложение, показать похожий сценарий и подвести пользователя к подтверждению системного окна Windows Hello. Идея показывать код подтверждения в приложении и затем сверять его с кодом в системном окне Windows Hello также не подходит: по результатам исследования системное окно Windows Hello нельзя кастомизировать в таком формате, а симуляция похожего поведения со стороны вредоносного приложения все равно остается возможной. Поэтому такие меры можно рассматривать только как слабое снижение риска ошибки пользователя, но не как техническое исправление.
## 4. Что выглядит рабочим направлением защиты
Краткосрочно: ограничить или отключить Windows Hello как самостоятельный способ разблокировки мастер-ключа на Windows. Безопаснее требовать пароль или использовать схему, где Windows Hello является только дополнительным фактором. Позднее выполнить: изучить упаковку через MSIX, AppContainer и Win32 App Isolation. Есть предположение, что при наличии идентичности приложения Windows может учитывать Package Family Name и изолировать credential на уровне приложения, но это пока не подтверждено прямым ответом Microsoft.
## 5. Открытые вопросы и следующие шаги
В Jira зафиксировано 7 открытых обращений, по которым ожидаются ответы. Основной вопрос сейчас находится в первом обращении: если приложение A упаковано в MSIX и работает внутри AppContainer, а приложение B запущено от имени того же пользователя и знает имя credential, сможет ли приложение B открыть этот credential через KeyCredentialManager.OpenAsync. Нужен прямой ответ да или нет. До получения этого ответа MSIX/AppContainer нельзя считать готовым исправлением, только направлением темы.
## Основные темы полного исследования
1. Подтвердить официальную границу безопасности KeyCredentialManager для обычных Win32-приложений.
2. Проверить, меняет ли MSIX, AppContainer или Win32 App Isolation доступ к credential между процессами одного пользователя.
3. Спроектировать схему, где Windows Hello не является единственным способом доступа к мастер-ключу.
4. Найти альтернативы для долгосрочной архитектуры: пароль плюс Windows Hello, разделенный ключ, passkeys для сценариев работы с сид-фразой.
## Предварительное заключение
На текущий момент не подтвержден способ полностью закрыть этот сценарий только настройками KeyCredentialManager для обычного Win32-приложения. Наиболее безопасная трактовка: Windows Hello в этой модели подтверждает пользователя, но не гарантирует, что запрос пришел от нужного приложения. Поэтому для защиты ценных локальных секретов Windows Hello нельзя считать единственным барьером. Нужно либо добавлять второй независимый фактор на уровне приложения, либо подтверждать через Microsoft, что MSIX/AppContainer действительно создают нужную границу доступа.
## 6. Что нужно сделать
1. Протестировать сборку кошелька под AppContainer. Это единственная конфигурация, где теоретически возможна изоляция credential на уровне приложения через Package SID в токене процесса, но потребуется дополнительные возможности, а у Flutter нет готового пути. MSIX-упаковка Win32-приложения AppContainer не дает: packaged desktop app по умолчанию работает в full trust, credential остаются в границе пользователя, а не приложения. Изоляция начинается только когда процесс реально запущен внутри AppContainer. 

Первый вариант: сборка под UWP, нативный путь к AppContainer, но Flutter так не умеет, поддержка UWP-embedder была свернута и удалена из фреймворка в 2022 году, см. https://github.com/flutter/flutter/issues/14967. 

Второй вариант: оставить текущую Win32-сборку, но вручную править MSIX-манифест сборщика, включить режим Partial trust через uap10:TrustLevel=appContainer, убрать runFullTrust, добавить нужные capabilities - https://learn.microsoft.com/en-us/windows/msix/msix-container. Даже если AppContainer включится, результат не гарантирован: у Flutter есть сообщения о крашах в MSIX/AppContainer sandbox, которые не воспроизводятся при запуске exe напрямую, см. https://github.com/flutter/flutter/issues/183313. Поэтому надо дождаться ответов Microsoft по открытым обращениям, особенно может ли unpackaged-процесс того же пользователя открыть credential, созданный AppContainer-приложением; если изоляция подтверждается, запланировать POC Win32 плюс MSIX с Partial trust и проверить стабильность кошелька и cross-process-доступ к credential; не считать plain MSIX или просто другой PFN исправлением, это не AppContainer.
