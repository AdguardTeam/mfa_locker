AW-2956 · Investigation follow-up · Windows only

Validation & Critique — the "Two-Part Key + Windows Hello" approach

An assessment of approach_of_windows_hello_usage.md (attached to AW-2956, 2026-07-02): a scheme that splits the master key into a password-derived part and a DPAPI device_secret, gating recovery of the second part behind UserConsentVerifier (Windows Hello).

Ticket: AW-2956 (P2, Code Review) Proposal author: R. Prudchenko Threat model: same-user malware, no elevation Reviewed against: conclusion/ 00–05 + AW-2957 Date: 2026-07-02
Bottom line The scheme does not fix AW-2956 — and one of its two variants re-creates it.

Against the ticket's actual threat (same-user malware), the proposal provides no cryptographic protection beyond the password itself. Its two "Windows-Hello" ingredients are both non-barriers to that adversary:

  • UserConsentVerifier is a bypassable client-side presence check, not a cryptographic factor — malware simply skips it.
  • DPAPI device_secret is scoped to the user account, not the app — any same-user process can CryptUnprotectData it (this is the exact root cause already documented in gaps §G8, and the mechanism behind Bitwarden's CVE-2023-27706).

So the security of the whole envelope collapses to the password. That makes the scheme, at best, equal to the already-shipped password-only posture (AW-2957) but more complex — and, in the variant where the password/derived key is cached for "indefinite" reuse, strictly worse: it rebuilds the AW-2956 vulnerability with an extra DPAPI layer that malware peels off trivially. It is defensible only if re-labelled honestly as UX convenience over a password root of trust (the "Quick Unlock" pattern already in action plan §4) — never as a way to make Windows Hello a safe standalone factor.

1. What the proposal actually says

The document surveys how 1Password, Bitwarden and several wallets use Windows Hello, then lands on a single recommendation: split the master key into two parts and combine them only after a Windows Hello check. It describes two variants of the same idea, and it is important to separate them because they fail differently.

Variant A — in-memory password caching with a Hello-gated second part

(§ "Ресерч с использованием Windows Hello", 2nd paragraph.) On entry the user always types the password; the first part of the master key is derived from it and held in memory for ~5 minutes. During that window Windows Hello can retrieve the second part. After the window the first part is wiped and the password is required again. The document itself states the flaw: "part of the key is held in memory — if it can be accessed, obtaining the second part is trivial, because you can raise the same verification window the app uses."

Variant B — DPAPI device_secret combined into a KEK, gated by UserConsentVerifier

(§ "Подход с разделением ключа на 2 части".) The concrete, named scheme:

1. User enters password (the doc: "can be saved and used later for an indefinite time")
2. Derive password_key (Argon2/PBKDF2)
3. Call UserConsentVerifier → get Verified/NotVerified
4. if Verified → call CryptUnprotectData (DPAPI)
5. Recover device_secret (DPAPI-bound to device+user)
6. Mix password_key + device_secret → KEK
7. KEK decrypts DEK
8. DEK decrypts the seed phrase for the duration of the operation

The document's own conclusion: "the only working method at present is the two-part split; other options are derivatives of it." The rest of this review evaluates whether that claim holds.

2. Validation against the threat model

AW-2956 has a precise, documented adversary (problem §4, gaps §G3): malware running as the same Windows user, without elevation. That adversary can read %APPDATA%, read the encrypted vault file, scrape process memory of a running process, call any user-scoped Windows API, and raise the genuine Windows Hello prompt. A proposal "fixes" AW-2956 only if it prevents that adversary from recovering the seed phrases after — at most — one careless user gesture.

Test each ingredient of the proposal against exactly that adversary. Both fail, for the same structural reason the whole investigation already established: on unpackaged Win32, no OS primitive binds a local secret to the application; the boundary is the user.

3. Five load-bearing flaws

Flaw 1Fatal

UserConsentVerifier is not a cryptographic factor

UserConsentVerifier.RequestVerificationAsync() returns an enum (Verified, Canceled, DeviceNotPresent…). It releases no key material, signs nothing, and produces no output that feeds the KEK. In the proposed flow, step 3→4 is literally an if (result == Verified) { CryptUnprotectData(...) } branch inside the app's own process. Nothing at the OS level ties a successful verification to the subsequent decryption.

Malware does not need to pass this check — it omits it entirely and calls CryptUnprotectData directly. This is the textbook "client-side authorization" anti-pattern; Clément Notin's public research on Windows Hello makes exactly this point ([7]). Contrast with the current (pre-AW-2957) design, which at least required a real KeyCredentialManager.RequestSignAsync signature — the proposal is weaker on this axis, not stronger.

Flaw 2Fatal

DPAPI device_secret is user-scoped, not app-scoped

CryptProtectData/CryptUnprotectData bind data to the user account + machine, never to the calling application, for unpackaged Win32. This is already recorded verbatim in gaps §G8: "DPAPI, DPAPI-NG/CNG, Credential Locker — all authorise by user/SID, none by application identity for unpackaged Win32." Therefore device_secret is recoverable by any same-user process.

The proposal's premise — "device_secret is accessible only after passing UserConsentVerifier" — is false as a security property. The app chooses to call the verifier first; the OS does not enforce it. This is precisely the mechanism of Bitwarden's CVE-2023-27706 ("Bitwarden Heist") [6]: a DPAPI-protected secret that any same-user process could retrieve. The proposal re-introduces the vulnerable pattern Bitwarden was forced to remove.

Flaw 3Design

Splitting a key gives nothing when both parts share one adversary

Secret-splitting only buys security when the parts sit behind different trust boundaries. Here, against same-user malware, both parts are reachable: device_secret via DPAPI (Flaw 2), and password_key via the password (keyloggable, or scrapable from memory while cached). Two ingredients, one adversary, zero added boundary. The split is security theatre against AW-2956 — it only looks like defense-in-depth.

The one place the split does something real is a different threat: offline theft of the vault file for cracking on another machine. DPAPI device-binding genuinely prevents that (you also need the machine). But the Argon2id password KDF already provides strong offline resistance, and offline theft is not AW-2956. So the benefit is marginal and mis-aimed.

Flaw 4Fatal (Variant B)

"Save the password for an indefinite time" rebuilds AW-2956

Variant B's step 1 says the password "can be saved and used later for an indefinite time." If the password (or password_key) is persisted so that Hello alone re-unlocks the wallet, then whatever storage holds it becomes the new target — and that storage is, once again, only user-scoped (secure storage, DPAPI, or a Hello-gated blob). Same-user malware reads it. The result is the original vulnerability with an extra DPAPI wrapper it removes in one call: read the persisted key material, raise one Hello prompt (or none), recover the seed phrases. This configuration is strictly worse than AW-2957 and must not ship.

Flaw 5Framing

It cites the vulnerable pattern, not the fixed one

The proposal opens by noting 1Password/Bitwarden use UserConsentVerifier and unlock "only at session start." Two corrections. (a) Bitwarden's fix for CVE-2023-27706 moved to a live KeyCredentialManager Hello interaction and away from the store-a-DPAPI-secret pattern — the proposal points at the pre-fix behaviour [6]. (b) 1Password is explicit ([8]) that the vault stays "encrypted with your account password and Secret Key… even with Windows Hello turned on" — Hello re-requests the password periodically. In both products the password/secret is the root of trust and Hello is convenience. The proposal borrows their surface (UserConsentVerifier) without their actual security model.

4. Where the security actually rests

Strip away the non-barriers (Flaws 1–2) and the envelope reduces to one factor — the password — with a biometric gesture bolted on for UX. The scheme then lands in one of three configurations, all determined by where the password lives:

ConfigurationConvenience vs AW-2957Security vs AW-2956 (same-user malware)Net
Password typed every unlock (no caching) None — you type the password anyway; Hello is decoration ≈ AW-2957 (password is the barrier; Hello adds nothing) Pointless equal security, more code, no UX gain
Password / key persisted for reuse (Variant B "indefinite") High (biometric re-unlock) Worse — persisted key is user-scoped; malware reads it + one/zero Hello taps → seeds Rebuilds AW-2956 must not ship
Derived key cached in memory, short TTL (Variant A) Moderate (skip re-typing within the window) = AW-2957 at cold start; window is memory-scrapable (nothing on Windows stops this) Acceptable as convenience = the "Quick Unlock" pattern, if framed honestly
Key insight

The only configuration that is both more convenient than password-only and not a rebuild of AW-2956 is Variant A (short-lived in-memory session cache). And that one is convenience, not a security boundary — it matches how KeePassXC "Quick Unlock" and post-fix Bitwarden operate. So the proposal's real, defensible core is already captured by action plan §4 (Hybrid "Quick Unlock") — but arrived at through an unsound argument (it credits Hello/DPAPI with protection they don't provide).

5. What is genuinely useful in it

  • Password becomes mandatory. Unlike the original design (biometric = a standalone bio KeyWrap of the same master key — see problem §2), this scheme makes the password structurally required. That is the correct direction and matches industry.
  • DPAPI device-binding as defense-in-depth against offline/cross-machine attacks on a stolen vault file — cheap, real, but aimed at a threat the password KDF already largely covers, and irrelevant to AW-2956.
  • A time-boxed session cache (Variant A's 5-minute window) is the right shape for a convenience layer.
  • Honest self-assessment. The document does admit the in-memory weakness — it simply understates how completely that (plus Flaws 1–2) defeats the stated goal.

7. Corrections & additions

  1. Name the adversary in the doc. The proposal never states its threat model. Add it explicitly (same-user, non-elevated malware) — every claim's truth value depends on it, and being explicit would have surfaced Flaws 1–2 immediately.
  2. Drop UserConsentVerifier as a security element. If Hello is used at all, it must be a live KeyCredentialManager operation whose output is cryptographically consumed (a signature over a fresh challenge), not a boolean the app trusts. Even then it is convenience, not a boundary (see gaps §G5).
  3. Never persist the password or a full password-equivalent key. If convenience is wanted, cache a derived, revocable session key in memory only, with a short TTL, and require the full password on cold start / after reboot.
  4. If Hello returns, sign a fresh random challenge — not a constant. The current constant locker_authentication_request yields an offline-reproducible KEK (gaps §G5/G6). A per-session nonce, TPM-backed, result in memory only, removes the "sign once, derive forever" property.
  5. Apply the cheap defense-in-depth only alongside the above: per-install random tag (S2) and per-install random data-to-sign (S3). They do not change the boundary but raise cost for untargeted, scaled malware. They are worthless on their own.
  6. Account for the build cost. Re-introducing biometric_cipher / KeyCredentialManager on Windows resurfaces the known /await + <experimental/coroutine> MSVC build break on newer toolchains — a real implementation cost that must be budgeted, not discovered late.

8. Other / better options

Option A — Keep password-only permanent (AW-2957) Lowest risk

Already shipped, closes AW-2956 deterministically, matches 1Password/Bitwarden/KeePassXC. Cost: no biometric convenience on Windows. If the two-part scheme's real security is "equal to password-only" (Flaws 1–3), then this is the same security for far less code. This is the honest baseline the proposal must beat — and against the stated threat, it cannot.

Option B — "Quick Unlock" done correctly Recommended if convenience is required

This is the salvageable form of the proposal, and it is already in action plan §4:

  • Password is the root of trust; required on every cold start / after reboot.
  • Hello only short-circuits re-unlock within an already-authenticated session — never a standalone equal-to-password unlock.
  • The Hello-derived value is TPM-backed, signs a fresh per-session challenge, and is held in memory only.

Explicitly convenience, not a boundary: it still can't stop same-user malware racing the user (nothing on Windows does), but it removes the offline-reproducible-KEK property that made AW-2956 severe. Frame it as such and it is acceptable; frame it as "safe Hello" and it misleads.

Option C — AppContainer / Win32 App Isolation Gated on an experiment

The only path that could restore real app-binding on Windows — but it is preview-only (Win11 24H2+), has no Flutter packaging path, risks every native plugin, and its benefit against an unpackaged attacker is unproven. It must be gated on the empirical experiment in action plan §2 and the feasibility analysis in appcontainer-feasibility-and-plan.md. Not a near-term fix, and the team has already deprioritised it (Jira, 2026-06-19).

Option D — Hardware root of trust Long-horizon

The only way to make a local high-value secret genuinely resistant to same-user malware on Windows is to keep the signing key off the general-purpose OS surface — a hardware device (Ledger-style) or an external authenticator. Large scope; noted for completeness, not proposed here.

9. Recommendation

Do
  • Do not adopt the two-part scheme as a fix. Against AW-2956's threat it is equal to password-only at best (Flaws 1–3), and dangerous in its persisted-password variant (Flaw 4).
  • Keep AW-2957 (password-only) as the current, correct posture; add the launch-time stale-key cleanup from action plan §1.3.
  • If — and only if — biometric convenience on Windows is a product requirement, implement Option B (Quick Unlock), taking the salvageable ideas from the proposal (mandatory password, session cache) but discarding its security claims about UserConsentVerifier and DPAPI. Re-label it "convenience," not "secure Hello."
Don't
  • Persist the password / master-equivalent key so Hello alone re-unlocks (rebuilds AW-2956).
  • Treat UserConsentVerifier success as authorization for decryption.
  • Present any in-process, unpackaged Win32 scheme as making Windows Hello a safe standalone unlock — the OS boundary is the user, not the app.

This assessment does not change the investigation's governing principle (action plan §0): on unpackaged Win32, no OS primitive binds a local secret to the application, so Windows Hello cannot be a safe standalone unlock for a high-value secret. The proposal is a new attempt at the "algorithmic approach" requested on 2026-06-29, but it does not escape that principle — it re-encounters it.
